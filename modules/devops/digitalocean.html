11 Module DevOps

Pratique : déploiement complet sur DigitalOcean

On boucle la boucle. Une vraie application — frontend web, API backend Node.js, PostgreSQL, et une app mobile sur la même API — déployée de bout en bout sur DigitalOcean, en réutilisant chaque brique du module.

Le cas concret. On assemble tout : Terraform provisionne DOKS + PostgreSQL + Registry + Load Balancer ; la CI build, teste, scanne et pousse l'image ; le pattern GitOps (ArgoCD) déploie ; Prometheus/Grafana surveillent. Chaque étape renvoie au chapitre théorique correspondant.

A · Le parcours complet, du code à la prod

L'organigramme chronologique — chaque étape est annotée du chapitre du module qui la couvre :

1
Le dev code & pushChap. 2 · Git

Développement sur une branche feature/*, commits conventionnels, puis git push.

2
Pull Request → review → merge sur mainChap. 2 · Git

Revue de code, CI verte & approbations requises (branch protection), puis squash-merge sur main.

3
Pipeline CI : lint → tests → build → scan TrivyChap. 3 & 9 · CI / Sécu

GitHub Actions valide le code ; l'image est scannée (CVE HIGH/CRITICAL → build cassé).

4
Build image Docker → push sur le Registry DOChap. 4 · Docker

Image multi-stage taguée par le SHA du commit, poussée sur le DigitalOcean Container Registry.

5
Mise à jour du repo GitOps (nouveau tag)Chap. 7 · GitOps

La CI bump le tag d'image dans les values Helm du repo de config — pas de déploiement direct.

6
ArgoCD détecte & synchronise sur DOKSChap. 5 & 7 · K8s / GitOps

ArgoCD (pull) voit le commit et applique l'état désiré sur le cluster DigitalOcean Kubernetes.

7
Kubernetes : rolling update des podsChap. 5 · K8s

Remplacement progressif des pods (maxUnavailable: 0) → mise à jour sans coupure.

8
Requêtes → LB DO → API Gateway → servicesChap. 9 · Sécurité

Web & mobile passent par le Load Balancer, l'API Gateway valide le token OAuth2/OIDC, puis route vers les services.

9
Monitoring en continu & alertesChap. 8 · Observabilité

Prometheus scrape les métriques, Grafana affiche les golden signals, Alertmanager notifie en cas d'anomalie — et la boucle recommence.

B · L'infra DigitalOcean en Terraform

Un seul terraform apply provisionne toute la fondation : VPC, cluster DOKS, PostgreSQL managée, Container Registry et Load Balancer.

main.tf

main.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    digitalocean = {
      source  = "digitalocean/digitalocean"
      version = "~> 2.40"
    }
  }
  # State distant sur DigitalOcean Spaces (compatible S3) — voir chap. 6
  # backend "s3" { ... }
}

provider "digitalocean" {
  token = var.do_token
}

# --- Réseau privé dédié ---
resource "digitalocean_vpc" "main" {
  name     = "${var.project}-${var.environment}-vpc"
  region   = var.region
  ip_range = "10.20.0.0/16"
}

# --- Cluster Kubernetes managé (DOKS) ---
resource "digitalocean_kubernetes_cluster" "doks" {
  name     = "${var.project}-${var.environment}"
  region   = var.region
  version  = var.k8s_version
  vpc_uuid = digitalocean_vpc.main.id

  node_pool {
    name       = "worker-pool"
    size       = var.node_size
    auto_scale = true                 # autoscaling du pool
    min_nodes  = var.node_count
    max_nodes  = var.max_nodes
  }
}

# --- Base de données PostgreSQL managée ---
resource "digitalocean_database_cluster" "postgres" {
  name                 = "${var.project}-${var.environment}-pg"
  engine               = "pg"
  version              = "16"
  size                 = var.db_size
  region               = var.region
  node_count           = 1
  private_network_uuid = digitalocean_vpc.main.id   # accessible en privé
}

# --- Pare-feu DB : n'autoriser que le cluster ---
resource "digitalocean_database_firewall" "pg" {
  cluster_id = digitalocean_database_cluster.postgres.id
  rule {
    type  = "k8s"
    value = digitalocean_kubernetes_cluster.doks.id
  }
}

# --- Container Registry privé ---
resource "digitalocean_container_registry" "registry" {
  name                   = var.registry_name
  subscription_tier_slug = "basic"
  region                 = var.region
}

# --- Load Balancer public (TLS) devant le cluster ---
resource "digitalocean_loadbalancer" "public" {
  name     = "${var.project}-${var.environment}-lb"
  region   = var.region
  vpc_uuid = digitalocean_vpc.main.id

  forwarding_rule {
    entry_port       = 443
    entry_protocol   = "https"
    target_port      = 30080          # NodePort de l'ingress controller
    target_protocol  = "http"
    certificate_name = var.tls_cert_name
  }

  healthcheck {
    port     = 30080
    protocol = "http"
    path     = "/healthz"
  }
}
LB explicite vs Service type=LoadBalancer

Sur DOKS, un Service Kubernetes de type LoadBalancer provisionne automatiquement un Load Balancer DO. On le déclare ici explicitement pour la clarté et pour le contrôler par Terraform ; en pratique, on gère souvent le LB via l'ingress controller + une annotation.

C · GitOps avec ArgoCD sur le cluster

Installation d'ArgoCD sur DOKS

bash
# Récupérer le kubeconfig du cluster fraîchement provisionné
terraform output -raw kubeconfig > kubeconfig.yaml
export KUBECONFIG=$PWD/kubeconfig.yaml
# (ou) doctl kubernetes cluster kubeconfig save monapp-prod

# Installer ArgoCD
kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Mot de passe admin initial
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d

# Accéder à l'UI en local
kubectl port-forward svc/argocd-server -n argocd 8080:443

L'Application ArgoCD

Elle pointe vers le repo GitOps et le chart du backend, avec les values de prod :

argocd/applications/backend-prod.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: backend-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/acme/monapp-gitops.git
    targetRevision: main
    path: charts/backend
    helm:
      valueFiles:
        - values-prod.yaml          # values spécifiques à la prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true                # corrige tout drift
    syncOptions:
      - CreateNamespace=true

D · Le pipeline CI/CD (build → GitOps)

Le workflow va du build jusqu'au commit dans le repo GitOps : il ne touche jamais le cluster directement — ArgoCD s'en charge (pattern GitOps du chapitre 7).

.github/workflows/deploy.yml
name: build-and-deploy

on:
  push:
    branches: [ main ]

env:
  REGISTRY: registry.digitalocean.com/monapp-registry
  IMAGE: backend

jobs:
  ship:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # --- 1. Qualité (chap. 3) ---
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run lint
      - run: npm test

      # --- 2. Build de l'image (chap. 4) ---
      - name: Build image
        run: docker build -t "$REGISTRY/$IMAGE:${{ github.sha }}" .

      # --- 3. Scan de sécurité (chap. 9) ---
      - name: Scan Trivy
        uses: aquasecurity/trivy-action@0.24.0
        with:
          image-ref: "${{ env.REGISTRY }}/${{ env.IMAGE }}:${{ github.sha }}"
          severity: HIGH,CRITICAL
          exit-code: '1'                 # casse le build si CVE critique

      # --- 4. Push vers le registry DigitalOcean (chap. 4) ---
      - name: Login DigitalOcean
        uses: digitalocean/action-doctl@v2
        with:
          token: ${{ secrets.DIGITALOCEAN_TOKEN }}
      - run: doctl registry login
      - run: docker push "$REGISTRY/$IMAGE:${{ github.sha }}"

      # --- 5. Mise à jour du repo GitOps (chap. 7) : PAS de kubectl apply ---
      - name: Checkout du repo GitOps
        uses: actions/checkout@v4
        with:
          repository: acme/monapp-gitops
          token: ${{ secrets.GITOPS_PAT }}   # token avec droits d'écriture
          path: gitops

      - name: Bump du tag d'image
        run: |
          cd gitops
          yq -i '.image.tag = "${{ github.sha }}"' charts/backend/values-prod.yaml
          git config user.name  "ci-bot"
          git config user.email "ci@acme.dev"
          git commit -am "chore(deploy): backend ${{ github.sha }}"
          git push
      # -> ArgoCD détecte ce commit et synchronise le cluster automatiquement.

La boucle est bouclée

Du git push jusqu'aux dashboards de production, chaque maillon du module s'emboîte : Git déclenche la CI, qui produit une image Docker scannée, poussée sur le registry ; le GitOps (ArgoCD) déploie sur Kubernetes provisionné par Terraform, sécurisé par l'API Gateway et OIDC, observé par Prometheus/Grafana. C'est ça, le DevOps : une chaîne automatisée, mesurée et réversible — de l'idée à la production.

🎉 Le parcours principal est bouclé — de la culture à la mise en production sur un cloud réel. Envie d'aller plus loin ? Le chapitre bonus traite de la scalabilité & la montée en charge.

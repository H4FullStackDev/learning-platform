Scalabilité & Montée en charge

Encaisser un pic de trafic sans tomber : dimensionnement automatique, cache, files de messages, scaling de la base, résilience et tests de charge. Les outils et les patterns pour passer de 10 à 100 000 requêtes/s.

Le problème. Une architecture qui marche à 100 utilisateurs peut s'effondrer à 100 000. La scalabilité, c'est la capacité à absorber la charge en ajoutant des ressources, idéalement automatiquement. Ce chapitre bonus rassemble les leviers — de l'autoscaling Kubernetes aux files de messages — et les patterns de résilience qui vont avec.

Deux façons de scaler

Vertical (scale up)

On donne plus de ressources à une instance (CPU, RAM). Simple, mais plafonné par la taille max d'une machine et sujet à un point unique de défaillance. Nécessite souvent un redémarrage.

Horizontal (scale out)

On ajoute plus d'instances derrière un load balancer. Quasi illimité, résilient, et automatisable. C'est l'approche cloud-native — celle du reste de ce chapitre.

Le prérequis absolu : être stateless

On ne peut multiplier les instances que si elles ne gardent aucun état local : les sessions vont dans Redis (pas en mémoire du pod), les fichiers dans un stockage objet (S3/Spaces), et n'importe quelle instance peut traiter n'importe quelle requête. Un service stateful ne scale pas horizontalement.

Répartition de charge

Scaler horizontalement suppose un load balancer qui distribue le trafic. Deux niveaux, plusieurs algorithmes :

AspectDétail
L4 (transport)Répartit au niveau TCP/UDP, très rapide, sans connaître le contenu HTTP.
L7 (application)Comprend HTTP : routage par chemin/host, terminaison TLS, sticky sessions (cf. Ingress, ch. 5).
Round-robinChaque instance à tour de rôle — simple, par défaut.
Least connectionsVers l'instance la moins chargée — mieux pour des requêtes hétérogènes.
IP hashUn client tombe toujours sur la même instance (affinité).
Health checksUne instance non saine est retirée du pool automatiquement.

Autoscaling Kubernetes

Le cœur du sujet en environnement conteneurisé. Trois autoscalers complémentaires :

  • HPA (Horizontal Pod Autoscaler) — ajuste le nombre de pods selon des métriques.
  • VPA (Vertical Pod Autoscaler) — ajuste les requests/limits d'un pod (scale up).
  • Cluster Autoscaler — ajoute/retire des nœuds quand les pods ne tiennent plus (le node pool auto_scale vu au ch. 11).

hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web                       # le Deployment à scaler
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70    # scale si CPU moyen > 70 %
    - type: Pods                     # métrique custom : requêtes/s par pod
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"       # au-delà de 100 req/s/pod -> scale out
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # attendre 5 min avant de réduire (anti-flapping)
Scaler sur les bonnes métriques

Le CPU ne raconte pas toute l'histoire. Pour une API, les requêtes/seconde ou la latence reflètent bien mieux la charge réelle ; pour un worker, c'est la longueur de la file. Les métriques custom (via Prometheus Adapter / KEDA) rendent l'autoscaling bien plus pertinent que le CPU seul. Et n'oubliez pas des requests corrects (ch. 5) : sans eux, le HPA calcule dans le vide.

Mettre en cache pour soulager la charge

Le meilleur moyen d'encaisser la charge, c'est de ne pas la traiter. Chaque couche de cache absorbe une partie du trafic avant qu'il n'atteigne la base :

Client
CDNassets statiques
Rediscache applicatif
PostgreSQLsource de vérité
  • CDN — sert les assets (JS, CSS, images) au plus près de l'utilisateur ; décharge totalement l'origine pour le statique.
  • Cache applicatif (Redis) — mémorise les résultats coûteux (requêtes, calculs). Pattern cache-aside : on lit le cache, et en cas de miss on lit la base puis on remplit le cache.
  • Invalidation & TTL — le vrai défi. Un TTL court limite les données périmées ; on invalide explicitement à l'écriture pour les données critiques.
cache-aside (Node.js)
async function getProduit(id) {
  const cle = `produit:${id}`;
  const cache = await redis.get(cle);
  if (cache) return JSON.parse(cache);        // HIT : on ne touche pas la base

  const produit = await db.query('SELECT * FROM produits WHERE id = $1', [id]);
  await redis.set(cle, JSON.stringify(produit), 'EX', 300);  // MISS : on remplit (TTL 5 min)
  return produit;
}

Absorber les pics avec des files de messages

Quand un pic dépasse la capacité de traitement, une file de messages (RabbitMQ, Kafka) joue le rôle d'amortisseur : l'API accepte vite les demandes et les empile ; des workers les consomment à un rythme soutenable. On découple la réception du traitement.

  • Lissage des pics — un afflux de 10 000 tâches en 1 s est traité en quelques minutes sans rien casser.
  • Découplage — l'API répond immédiatement (« pris en compte ») ; le traitement lourd (e-mails, PDF, vidéos) se fait en arrière-plan.
  • Backpressure — si la file s'allonge, on scale les workers (HPA sur la longueur de file via KEDA), on ralentit les producteurs, ou on rejette proprement.

Scaler la base de données

C'est souvent le goulot d'étranglement final — et le plus difficile à scaler, car la base est stateful. Dans l'ordre :

App
PgBouncerpool de connexions
Primaryécritures
Replicaslectures
  • Connection pooling (PgBouncer) — les connexions Postgres sont coûteuses ; un pool les mutualise et évite de saturer la base sous forte concurrence. Premier réflexe.
  • Read replicas — on route les lectures vers des réplicas (souvent 80–90 % du trafic), les écritures vers le primary. DigitalOcean gère ça en managé.
  • Index & requêtes — avant de scaler, optimiser : une requête lente scalée reste lente, en plus cher.
  • Partitionnement / sharding — en dernier recours, répartir les données sur plusieurs bases (complexe : à éviter tant que possible).

Rester debout sous la charge : la résilience

Scaler ne suffit pas : il faut dégrader proprement plutôt que de s'effondrer en cascade. Les patterns essentiels :

PatternRôle
TimeoutNe jamais attendre indéfiniment un service lent ; libérer la ressource.
Retry + backoffRéessayer avec un délai croissant & du jitter — sans marteler un service déjà en difficulté.
Circuit breakerAprès trop d'échecs, « couper le disjoncteur » vers un service en panne et échouer vite, le temps qu'il se rétablisse.
BulkheadCloisonner les ressources (pools séparés) pour qu'une panne n'en contamine pas d'autres.
Load sheddingSous surcharge, rejeter tôt l'excédent (HTTP 429) pour protéger le cœur du service.
Graceful degradationRépondre en mode dégradé (valeur en cache, fonctionnalité désactivée) plutôt qu'une erreur.

Tester la charge avant que les utilisateurs ne le fassent

On ne devine pas sa capacité, on la mesure. Un test de charge simule des milliers d'utilisateurs pour trouver le point de rupture avant la prod.

Exemple de scénario k6 — montée progressive, palier, pic, décrue, avec des seuils qui font échouer le test :

load-test.js (k6)
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 50 },    // montée à 50 utilisateurs virtuels
    { duration: '3m', target: 50 },    // palier stable
    { duration: '1m', target: 200 },   // pic de charge
    { duration: '2m', target: 0 },     // décrue
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'], // 95 % des requêtes sous 500 ms
    http_req_failed:   ['rate<0.01'],  // moins de 1 % d'erreurs
  },
};

export default function () {
  const res = http.get('https://api.exemple.com/produits');
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}

On surveille pendant le test : latence p95/p99, taux d'erreur, débit et saturation (les 4 golden signals du ch. 8), plus le déclenchement effectif du HPA. À intégrer dans la CI pour un smoke test de perf à chaque release.

Bonnes pratiques

Le mémo montée en charge
  • Stateless d'abord — sessions & fichiers hors des pods, sinon rien ne scale.
  • Autoscaler sur la charge réelle — RPS / latence / longueur de file, pas seulement le CPU.
  • Cacher agressivement — CDN + Redis ; le meilleur calcul est celui qu'on ne refait pas.
  • Découpler avec des files — pour lisser les pics et libérer l'API.
  • La base scale en dernier — pooling & read replicas avant tout sharding.
  • Dégrader gracieusement — timeouts, circuit breakers, load shedding : mieux vaut lent ou partiel que planté.
  • Tester la charge en continu — connaître son point de rupture avant les utilisateurs.

Voilà qui complète le tableau : un système DevOps n'est pas seulement automatisé, sécurisé et observé — il tient la charge, élastiquement et sans intervention. 🎉 Fin du module.

09 Module DevOps

Sécurité DevSecOps

Intégrer la sécurité tout au long de la chaîne — « shift left ». API Gateway, OAuth 2.0 et OpenID Connect (avec diagrammes de séquence), gestion des secrets et scan de vulnérabilités dans le pipeline.

DevSecOps, c'est déplacer la sécurité vers la gauche (shift-left) : au lieu d'un audit final, on l'intègre à chaque étape — code, dépendances, images, déploiement, runtime. Ce chapitre couvre le contrôle du trafic (API Gateway), l'identité (OAuth2/OIDC), les secrets et l'analyse automatisée des vulnérabilités.

A · API Gateway

Un API Gateway est le point d'entrée unique devant un ensemble de services. Il découple les clients des services : le client ne parle qu'à la gateway, qui route, sécurise et transforme, pendant que l'architecture interne peut évoluer librement.

📱 Clientsweb · mobile · partenaires
API Gatewaypoint d'entrée unique
service auth
service commandes
service paiement

Fonctionnalités clés

  • Routing — dirige chaque requête vers le bon service selon le chemin/host.
  • Rate limiting — limite le débit par client pour se protéger des abus et du déni de service.
  • Authentification centralisée — valide les tokens (JWT/OAuth) une fois, en amont, plutôt que dans chaque service.
  • Transformation — réécrit requêtes/réponses (headers, format, versions d'API).
  • Load balancing — répartit la charge sur les instances d'un service.

Rate limiting — exemples commentés

nginx.conf
# Zone de limitation : 10 requêtes/s par IP, 10 Mo de mémoire d'état
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

server {
    listen 80;

    location /api/ {
        # burst=20 : tolère un pic de 20 req ; nodelay : pas de mise en file
        limit_req zone=api burst=20 nodelay;
        limit_req_status 429;               # renvoie 429 Too Many Requests

        proxy_pass http://backend;
        proxy_set_header Authorization $http_authorization;
    }
}
kong.yml (déclaratif)
services:
  - name: api
    url: http://backend:3000
    routes:
      - name: api-route
        paths: ["/api"]
    plugins:
      - name: rate-limiting       # plugin natif de limitation
        config:
          minute: 600             # 600 requêtes/minute par consommateur
          policy: local
      - name: jwt                 # validation centralisée des tokens JWT

B · OAuth 2.0

OAuth 2.0 est un protocole d'autorisation déléguée : il permet à une application d'accéder à des ressources au nom d'un utilisateur, sans jamais manipuler son mot de passe.

Les 4 acteurs

👤 Resource Owner

L'utilisateur qui possède les données et donne (ou refuse) son consentement.

🖥️ Client

L'application qui veut accéder aux ressources au nom de l'utilisateur.

🔐 Authorization Server

Émet les tokens après authentification & consentement (ex. Keycloak, Auth0).

📦 Resource Server

L'API qui héberge les ressources et exige un access token valide.

Authorization Code Flow

Le flow le plus courant pour les applications web avec backend. L'utilisateur s'authentifie chez l'Authorization Server ; le client récupère un code temporaire qu'il échange (côté serveur, avec son secret) contre un token.

👤 User
🖥️ Client
🔐 Auth Server
📦 Resource
1 · « Se connecter »
2 · redirige vers /authorize
3 · page de login & consentement
4 · s'authentifie & consent
5 · redirige avec ?code=…
6 · échange code + client_secret
7 · access_token (+ refresh)
8 · GET /data + Bearer token
9 · données protégées

Authorization Code + PKCE recommandé

PKCE (Proof Key for Code Exchange) sécurise le flow pour les clients qui ne peuvent pas garder un secret (SPA, mobile). Le client génère un code_verifier aléatoire et envoie son hash (code_challenge) ; à l'échange, il prouve qu'il détient le verifier. Un code volé devient inutilisable. C'est aujourd'hui le standard recommandé pour tous les clients.

🔐 Auth Server
🔑 le client génère code_verifier + code_challenge = SHA256(verifier)
1 · /authorize + code_challenge

3 · s'authentifie
4 · redirige avec ?code=…
5 · échange code + code_verifier (aucun secret)
✅ l'Auth Server vérifie SHA256(verifier) == challenge
6 · access_token

Client Credentials Flow

Pour les échanges machine à machine (service → service), sans utilisateur. Le client s'authentifie avec ses propres identifiants et obtient un token pour lui-même.

⚙️ Client (service)
🔐 Auth Server
📦 Resource / API
1 · client_id + client_secret (grant=client_credentials)
2 · access_token
3 · appel API + Bearer token
4 · réponse
L'Implicit Flow est déprécié

L'ancien Implicit Flow renvoyait l'access token directement dans l'URL de redirection (fragment) — exposé dans l'historique, les logs, le referer. Sans PKCE ni échange serveur, il est vulnérable au vol de token. À ne plus utiliser : on lui préfère Authorization Code + PKCE partout, y compris pour les SPA.

 Access TokenRefresh Token

Scopes. Un scope limite ce que le token autorise : read:orders, write:profile… L'app ne demande que le strict nécessaire (moindre privilège), et l'utilisateur voit à quoi il consent. Exemple : scope=openid profile email read:orders.

C · OpenID Connect (OIDC)

La différence fondamentale

OAuth 2.0 = autorisation (« cette app peut-elle accéder à mes données ? »). OIDC = authentification (« qui est cet utilisateur ? »). OIDC est une couche d'identité par-dessus OAuth2 : il réutilise le même flow, mais ajoute un ID Token qui prouve l'identité de l'utilisateur.

L'ID Token : un JWT

L'ID Token est un JWT (JSON Web Token) en trois parties séparées par des points : header.payload.signature, chacune encodée en Base64URL.

eyJhbGciOiJSUzI1NiIsImtpZCI6ImFiYzEyMyJ9.eyJpc3MiOiJodHRwczovL2lkcC5leGVtcGxlLmNvbSIsInN1YiI6IjI0ODI4OSJ9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
Header — algorithme & clé Payload — les claims Signature — intégrité vérifiable

Décodé, le header indique comment vérifier la signature :

header (décodé)
{
  "alg": "RS256",        // algorithme de signature (RSA + SHA-256)
  "typ": "JWT",
  "kid": "abc123"        // identifiant de la clé publique (via jwks_uri)
}

Le payload contient les claims (affirmations sur l'utilisateur) :

payload (décodé)
{
  "iss": "https://idp.exemple.com/",   // issuer : qui a émis le token
  "sub": "248289761001",               // subject : l'identifiant unique de l'utilisateur
  "aud": "mon-app-client-id",          // audience : pour quel client ce token est destiné
  "exp": 1735689600,                   // expiration (timestamp Unix)
  "iat": 1735686000,                   // issued at : date d'émission
  "email": "alice@exemple.com",
  "email_verified": true,
  "name": "Alice Martin"
}

La signature (par la clé privée de l'IdP) garantit que le token n'a pas été altéré : le client la vérifie avec la clé publique récupérée via jwks_uri. Un JWT est signé, pas chiffré — ne jamais y mettre de secret.

Claims standards

ClaimSignification
issIssuer — l'autorité qui a émis le token
subSubject — identifiant unique et stable de l'utilisateur
audAudience — le(s) destinataire(s) prévu(s) du token
expExpiration — au-delà, le token est invalide
iatIssued At — date d'émission
nbfNot Before — pas valide avant cette date
jtiJWT ID — identifiant unique du token (anti-rejeu)

Discovery & /userinfo

Un IdP OIDC publie sa configuration à une URL standard : /.well-known/openid-configuration. Les clients y découvrent automatiquement tous les endpoints :

/.well-known/openid-configuration
{
  "issuer": "https://idp.exemple.com/",
  "authorization_endpoint": "https://idp.exemple.com/authorize",
  "token_endpoint": "https://idp.exemple.com/token",
  "userinfo_endpoint": "https://idp.exemple.com/userinfo",
  "jwks_uri": "https://idp.exemple.com/.well-known/jwks.json",
  "response_types_supported": ["code"],
  "scopes_supported": ["openid", "profile", "email"]
}

L'endpoint /userinfo renvoie les informations du profil pour un access token donné :

GET /userinfo → réponse
{
  "sub": "248289761001",
  "name": "Alice Martin",
  "email": "alice@exemple.com",
  "email_verified": true
}

D · Gestion des secrets

Un secret (mot de passe, clé API, token, certificat) ne doit jamais se trouver en clair dans le code, un fichier de config, une image Docker ou un .tfstate. Committer un secret, c'est le figer à jamais dans l'historique Git, exposé à quiconque clone le dépôt.

HashiCorp Vault

Vault centralise, chiffre et contrôle l'accès aux secrets. Deux notions clés : les secrets engines (modules qui gèrent un type de secret) et les secrets dynamiques — Vault génère des identifiants à la volée, avec une durée de vie courte (lease), puis les révoque automatiquement. Un identifiant fuité expire de lui-même.

bash — Vault
# Secret statique (KV v2)
vault kv put secret/app/db password="s3cr3t"
vault kv get -field=password secret/app/db

# Secret DYNAMIQUE : Vault crée des identifiants PostgreSQL éphémères
vault read database/creds/app-role
# -> username: v-token-app-x9f2
#    password: A1b2C3d4...
#    lease_duration: 1h        (révoqués automatiquement après 1h)

Alternatives managées

  • AWS Secrets Manager — stockage chiffré (KMS), rotation automatique, accès via IAM.
  • DigitalOcean — pas de service dédié : on utilise les App-Level Environment Variables chiffrées (encrypted) de l'App Platform, ou un Vault/Doppler externe.
  • Kubernetes — External Secrets Operator ou Sealed Secrets pour synchroniser ces coffres vers le cluster (cf. chapitre K8s).

La sécurité est distribuée sur tout le pipeline (« shift-left »), pas concentrée à la fin.
  • Trivy — scanne les images Docker (couches, paquets OS, dépendances) à la recherche de CVE. On casse le build sur HIGH/CRITICAL (cf. chapitre Docker).
  • Snyk — scanne les dépendances du projet (npm, pip…) et propose des correctifs de version.

Bonnes pratiques de sécurité

Le mémo DevSecOps
  • Shift-left — automatiser les contrôles de sécurité tôt et à chaque étape : casser le build sur une vulnérabilité critique.
  • Moindre privilège — scopes OAuth minimaux, IAM restreint, tokens courts, pas de root (conteneurs, K8s).
  • Auth Code + PKCE partout — jamais d'Implicit Flow ; valider systématiquement iss, aud, exp et la signature des JWT.
  • Zéro secret en clair — coffre-fort (Vault/Secrets Manager), secrets dynamiques, scan de secrets (gitleaks) dans la CI.
  • Défense en profondeur — API Gateway (rate limiting, authz centralisée) + TLS partout + scans SAST/DAST + rotation des secrets.

Comment lire le flux

  • Requête utilisateur — le navigateur charge la SPA depuis le CDN ; la SPA et l'app mobile appellent l'API Gateway, qui valide le token auprès de l'Identity Provider (OIDC), applique le rate limiting, puis route vers le Load Balancer et le cluster K8s. Les services lisent/écrivent dans PostgreSQL, Redis et communiquent en asynchrone via le broker.
  • Livraison (vert/rose) — un push déclenche la CI (build, test, scan) qui pousse l'image au Registry et bump le tag dans le repo GitOps ; ArgoCD détecte le commit et déploie sur le cluster (qui tire l'image du registry).
  • Observabilité (turquoise) — Prometheus scrape le cluster, alimente Grafana et Alertmanager ; la stack EFK centralise les logs.
  • Infra (ardoise) — Terraform provisionne en amont le VPC, le cluster, la base managée, le load balancer et le registry.

Monolithe modulaire ou microservices ?

Le bloc « backend » du schéma peut s'implémenter de deux façons. Aucune n'est « meilleure » dans l'absolu — c'est un compromis :

Monolithe modulaire

  • Un seul déployable, bien découpé en modules internes.
  • + Simple à développer, déployer, déboguer ; pas de latence réseau interne.
  • − Scaling en bloc ; un bug peut tout affecter.
  • Idéal : démarrage, petite équipe, domaine encore mouvant.

Microservices

  • Plusieurs services déployables indépendamment (comme sur le schéma).
  • + Scaling & déploiement ciblés ; équipes autonomes ; isolation des pannes.
  • − Complexité réseau, observabilité et données distribuées.
  • Idéal : grande échelle, plusieurs équipes, domaines stables.

Conseil pragmatique : commencer en monolithe modulaire, puis extraire en microservices les modules qui le justifient (charge, équipe dédiée). L'architecture ci-dessus reste identique : seul le contenu du bloc « cluster » change.

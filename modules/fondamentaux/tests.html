Tests & qualité de code

Comment être sûr que ton code marche — et qu'il continuera de marcher après tes prochaines modifications ? En écrivant des tests automatiques. On les met en place sur la mini-API.

La tranquillité d'esprit. Tester à la main à chaque changement, c'est long et on oublie des cas. Un test automatique est un petit programme qui vérifie ton code pour toi, en une commande. Son vrai super-pouvoir : t'avertir quand une modification casse quelque chose qui marchait (une « régression »).

Pourquoi tester ?

  • Attraper les bugs tôt — avant tes utilisateurs.
  • Modifier sans peur — si les tests passent toujours, tu n'as rien cassé.
  • Documenter le comportement — un test dit « voilà ce que ce code est censé faire ».

En Python, l'outil standard s'appelle pytest. Le principe : on écrit des fonctions dont le nom commence par test_, et dedans on utilise assert (« je vérifie que… »).

Ton premier test

Commençons par tester une simple fonction. Crée test_math.py :

test_math.py
def addition(a, b):
    return a + b

# pytest exécutera automatiquement toute fonction nommée test_...
def test_addition():
    assert addition(2, 3) == 5     # "je vérifie que 2 + 3 vaut 5"
    assert addition(-1, 1) == 0
terminal
pip install pytest
pytest
# -> 1 passed   ✅

assert ne dit rien si c'est vrai ; si c'est faux, pytest affiche exactement quoi a échoué. Change == 5 en == 6 pour voir un test échouer (rouge) : c'est instructif.

Tester la mini-API

Flask fournit un « client de test » qui appelle ton API sans lancer un vrai serveur — parfait pour les tests. Crée test_app.py à côté de ton app.py :

test_app.py
from app import app, init_db

def test_lister_taches():
    init_db()                       # prépare la base
    client = app.test_client()      # un "faux navigateur" pour tester
    reponse = client.get("/taches")
    assert reponse.status_code == 200      # la route répond bien

def test_creer_tache():
    client = app.test_client()
    reponse = client.post("/taches", json={"titre": "Tester mon code"})
    assert reponse.status_code == 201             # 201 = créé
    assert reponse.get_json()["titre"] == "Tester mon code"
Lance les tests de ton API Exercice
terminal
pytest -v
# -> test_app.py::test_lister_taches PASSED
#    test_app.py::test_creer_tache  PASSED
#    2 passed

Résultat attendu : deux tests verts. Ton API est maintenant vérifiée automatiquement — tu pourras la modifier en sachant tout de suite si tu casses quelque chose. 🛡️

Le linting & la lisibilité

Du code qui marche ne suffit pas : il doit être lisible (par les autres, et par toi dans six mois). Deux aides :

  • Un linter (ex. ruff, flake8) — analyse ton code et signale les erreurs de style, les variables inutilisées, les imports oubliés.
  • Un formateur (ex. black) — met automatiquement ton code au format standard (indentation, espaces) pour que tout le monde écrive pareil.

Pour la lisibilité « humaine » : des noms de variables clairs (total_prix plutôt que x), des fonctions courtes qui font une seule chose, et des commentaires quand le pourquoi n'est pas évident.

Erreurs fréquentes

Quand un test ne se comporte pas comme prévu
  • « pytest ne trouve aucun test » — le fichier doit s'appeler test_*.py et les fonctions test_*. C'est comme ça que pytest les repère.
  • AssertionError — un test échoue : c'est utile ! Lis le message, il montre la valeur obtenue vs attendue.
  • ModuleNotFoundError au lancement — pense à activer ton venv (chapitre 8) et à installer pytest dedans.
  • Des tests qui dépendent l'un de l'autre — chaque test doit pouvoir tourner seul. Évite qu'un test s'appuie sur les données créées par un autre.

Ton code est écrit, isolé, testé et lisible — le niveau d'un vrai projet. Dernière étape : l'empaqueter pour qu'il tourne partout, et franchir la porte du DevOps.

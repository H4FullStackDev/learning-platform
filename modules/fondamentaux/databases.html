Bases de données

Une application a besoin de mémoire : ranger des données et les retrouver rapidement. C'est le rôle de la base de données. On apprend le SQL sur SQLite, sans rien installer de lourd.

Le besoin. Au chapitre 3, on a écrit dans un fichier. Ça marche pour du texte simple, mais dès qu'on a beaucoup de données à chercher, trier, relier et partager entre plusieurs programmes, un fichier ne suffit plus. Une base de données est faite pour ça.

Pourquoi une base de données ?

Vois une base de données comme un tableur (type Excel) géant et intelligent, que plusieurs programmes peuvent interroger en même temps. Elle sait retrouver « tous les clients de Paris » parmi des millions de lignes en un clin d'œil, garantir que deux personnes n'écrasent pas la même donnée, et ne jamais rien perdre.

Les tables : lignes & colonnes

Dans une base relationnelle, les données vivent dans des tables — une table = une feuille de tableur. Chaque colonne est un champ (nom, email…), chaque ligne est un enregistrement (un utilisateur) :

idnomemail
1Alicealice@exemple.com
2Bobbob@exemple.com

Ci-dessus, la table utilisateurs : 3 colonnes, 2 lignes.

SQL : parler à la base

On interroge la base avec le SQL (Structured Query Language) — un langage proche de l'anglais. Quatre commandes couvrent l'essentiel (le « CRUD » : Create, Read, Update, Delete) :

SQL
-- Lire (Read)
SELECT * FROM utilisateurs;                 -- tout
SELECT nom FROM utilisateurs WHERE id = 1;  -- filtré

-- Créer (Create)
INSERT INTO utilisateurs (nom, email) VALUES ('Chloé', 'chloe@exemple.com');

-- Modifier (Update)
UPDATE utilisateurs SET email = 'alice@nouveau.com' WHERE id = 1;

-- Supprimer (Delete)
DELETE FROM utilisateurs WHERE id = 2;
N'oublie JAMAIS le WHERE

Un UPDATE ou DELETE sans WHERE s'applique à toutes les lignes de la table. DELETE FROM utilisateurs; vide la table entière ! Prends l'habitude d'écrire le WHERE en premier.

Clés primaires & étrangères

La clé primaire (primary key) est l'identifiant unique d'une ligne — la colonne id. Comme un numéro de sécurité sociale : deux personnes ne peuvent pas avoir le même.

La clé étrangère (foreign key) relie deux tables. Exemple : une table commandes a une colonne utilisateur_id qui pointe vers l'id de la table utilisateurs. C'est ce qui permet de dire « cette commande appartient à Alice » sans recopier tout son profil.

Pratiquer avec SQLite

SQLite est une base de données rangée dans un simple fichier, sans serveur à installer — parfaite pour apprendre (et pour notre projet du chapitre 6 !). L'outil sqlite3 ouvre un fichier de base et attend tes commandes SQL.

Ta première base de données Exercice

Dans ton terminal, ouvre une base (elle est créée si elle n'existe pas) :

terminal
sqlite3 ma-base.db

Le prompt devient sqlite>. Tape maintenant ces commandes SQL (chacune finie par ;) :

SQL
CREATE TABLE utilisateurs (id INTEGER PRIMARY KEY, nom TEXT, email TEXT);
INSERT INTO utilisateurs (nom, email) VALUES ('Alice', 'alice@exemple.com');
INSERT INTO utilisateurs (nom, email) VALUES ('Bob', 'bob@exemple.com');
SELECT * FROM utilisateurs;

Résultat attendu :

sortie
1|Alice|alice@exemple.com
2|Bob|bob@exemple.com

Tape .quit pour sortir. Tu viens de créer une table, d'y insérer des données et de les relire. 🎉 (Si sqlite3 n'est pas installé, télécharge-le sur sqlite.org.)

Aperçu : SQL vs NoSQL

Deux grandes familles de bases :

SQL (relationnel)

Des tables avec un schéma strict et des relations (clés). Idéal quand la structure des données est claire et stable. Ex. : PostgreSQL, MySQL, SQLite.

NoSQL

Un schéma souple (souvent des documents type JSON), pensé pour de très gros volumes. Ex. : MongoDB, Redis.

On approfondit énormément ce choix (index, réplication, cohérence…) dans la Formation System Design. Ici, retiens le SQL de base — il te suffira longtemps.

Erreurs fréquentes

Les pièges du SQL
  • Point-virgule oublié — chaque requête SQL se termine par ;. Sans lui, sqlite3 attend la suite (le prompt affiche ...>).
  • no such table — la table n'existe pas (faute de frappe, ou CREATE TABLE pas encore exécuté).
  • UNIQUE constraint failed — tu insères un id déjà pris (la clé primaire doit rester unique).
  • Un UPDATE/DELETE qui touche trop de lignes — le WHERE manquait (voir l'avertissement plus haut).

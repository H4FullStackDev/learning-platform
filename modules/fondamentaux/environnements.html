08 Fondamentaux Tech Intermédiaire

Environnements & dépendances

Isoler chaque projet, lister ses dépendances, gérer sa config sans jamais exposer de secret. On rend notre mini-API propre et reproductible.

Le ménage nécessaire. Au chapitre 6, on a fait pip install flask « dans le tas ». Ça marche… jusqu'au jour où deux projets ont besoin de versions différentes. On va apprendre à isoler chaque projet et à décrire ses dépendances pour que n'importe qui (ou un serveur) puisse le relancer à l'identique.

Le problème : les dépendances qui s'emmêlent

Une dépendance est une bibliothèque externe que ton projet utilise (comme Flask). Si tu installes tout globalement, tous tes projets partagent les mêmes versions : le projet A qui veut Flask 2 et le projet B qui veut Flask 3 entrent en conflit. Résultat : « ça marchait hier »…

L'environnement virtuel (venv)

La solution : un environnement virtuel — une boîte isolée par projet, avec ses propres dépendances, qui ne touche pas au reste. On la crée, on l'« active », et à partir de là pip install range tout dans la boîte.

terminal
cd mon-projet-api
python -m venv venv        # crée la boîte (un dossier "venv/")

# L'activer :
source venv/bin/activate       # macOS / Linux
source venv/Scripts/activate   # Windows (Git Bash)

# Ton prompt affiche maintenant (venv) au début : la boîte est active
pip install flask          # installé DANS la boîte, pas globalement

Pour sortir de la boîte : deactivate. Le dossier venv/ ne se partage jamais (il est propre à ta machine) — on le met dans le .gitignore (plus bas).

requirements.txt : la liste des courses

Comment quelqu'un d'autre (ou un serveur) sait-il quoi installer ? On fige la liste des dépendances dans un fichier requirements.txt :

terminal
# Génère la liste (avec les versions exactes installées)
pip freeze > requirements.txt

# Sur une autre machine, tout réinstaller d'un coup :
pip install -r requirements.txt

Le fichier ressemble à ça — on le commite dans Git (contrairement au dossier venv/) :

requirements.txt
Flask==3.0.0
click==8.1.7
Jinja2==3.1.2

Les variables d'environnement

Certaines valeurs changent selon où tourne l'app (ta machine, un serveur…) : le port, une URL, un mot de passe. On ne les met pas dans le code — on les lit dans l'environnement. Même code partout, config différente. En Python :

app.py (extrait)
import os

# os.getenv("NOM", valeur_par_defaut)
port = int(os.getenv("PORT", 5000))

app.run(debug=True, port=port)   # le port vient de l'environnement
terminal
PORT=8000 python app.py    # lance l'API sur le port 8000 sans changer le code

Ne JAMAIS commiter un secret

Un secret (mot de passe, clé d'API, token) ne doit jamais finir dans Git : une fois poussé, il reste dans l'historique pour toujours, visible de tous. On les range dans un fichier .env (local, non partagé), et on l'exclut de Git.

.env (jamais commité)
PORT=8000
SECRET_KEY=un-secret-a-ne-pas-partager
.gitignore
venv/            # la boîte, propre à chaque machine
__pycache__/     # fichiers temporaires de Python
*.db             # notre base SQLite
.env             # NOS SECRETS — surtout jamais dans Git

Le .gitignore liste ce que Git doit ignorer. On approfondit la gestion des secrets (coffres-forts, rotation…) dans la Formation DevOps → Sécurité.

Mets-le en pratique sur ta mini-API

Rends ton projet propre Exercice

Dans le dossier de ta mini-API (chapitre 6) :

terminal
python -m venv venv
source venv/bin/activate        # (ou .../Scripts/activate sur Windows)
pip install flask
pip freeze > requirements.txt   # fige les dépendances
python app.py                   # l'API tourne, isolée dans son environnement

Puis crée un fichier .gitignore (contenu ci-dessus) et fais un commit. Résultat attendu : git status ne propose ni venv/ ni .env — seulement ton code et requirements.txt. 🎯 Ton projet est maintenant reproductible et sûr.

Erreurs fréquentes

Les pièges de l'environnement
  • ModuleNotFoundError: flask alors que tu l'as installé — tu as oublié d'activer le venv (pas de (venv) dans ton prompt), ou tu l'as installé hors de la boîte.
  • Le dossier venv/ apparaît dans git status — ajoute-le au .gitignore (il est lourd et propre à ta machine).
  • Un .env commité par erreur — considère le secret comme compromis : change-le, et ajoute .env au .gitignore.
  • requirements.txt périmé — pense à refaire pip freeze après avoir installé une nouvelle dépendance.

Ton projet est propre, isolé et sans secret exposé. Reste une question de pro : comment être sûr qu'il marche, et qu'il continuera de marcher ? C'est le rôle des tests.

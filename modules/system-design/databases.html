04 System Design Intermédiaire

Bases de données en profondeur

La base est presque toujours le goulot d'étranglement final. Choisir SQL ou NoSQL, indexer, répliquer, partitionner : les décisions qui déterminent si votre système tient à l'échelle.

Le nerf de la guerre. On scale les serveurs d'app facilement (stateless). La base, elle, est stateful — c'est là que tout se complique. Ce chapitre couvre les quatre leviers dans l'ordre où on les tire : bon choix, bons index, réplication, puis partitionnement en dernier recours.

SQL ou NoSQL ?

CritèreSQL (relationnel)NoSQL
SchémaStrict, défini à l'avanceSouple, évolutif

Le NoSQL n'est pas « une » base mais quatre familles, chacune pour un usage :

  • Document (MongoDB) — objets JSON imbriqués, souple. Catalogues, profils.
  • Clé-valeur (Redis, DynamoDB) — accès ultra-rapide par clé. Cache, sessions.
  • Colonnes larges (Cassandra) — écritures massives distribuées. Séries temporelles, logs.
  • Graphe (Neo4j) — relations complexes. Réseaux sociaux, recommandations.
« NoSQL scale, SQL non » est un mythe

PostgreSQL tient des charges énormes avec réplicas & partitionnement. Le vrai critère, c'est votre modèle de données et vos besoins de cohérence. En cas de doute, commencez en SQL (plus sûr, plus flexible pour les requêtes) ; passez au NoSQL pour un besoin précis.

Indexation

Sans index, retrouver une ligne, c'est parcourir toute la table (full scan). Un index est une structure de données (souvent un B-tree) qui pointe directement vers les lignes — comme l'index d'un livre. Une recherche passe de O(n) à O(log n).

SQL
-- Sans index : scan complet de la table
SELECT * FROM users WHERE email = 'alice@exemple.com';

-- On crée un index sur la colonne interrogée
CREATE INDEX idx_users_email ON users (email);
-- -> la même requête devient quasi instantanée
L'index n'est pas gratuit

Chaque index accélère les lectures mais ralentit les écritures (il faut le mettre à jour) et consomme du stockage. On indexe les colonnes des WHERE, JOIN et ORDER BY fréquents — pas tout, à l'aveugle.

ACID vs BASE

Deux philosophies de cohérence, aux deux bouts du spectre :

ACID (SQL)

  • Atomicité — tout ou rien.
  • Cohérence — les règles sont toujours respectées.
  • Isolation — les transactions ne se marchent pas dessus.
  • Durabilité — une fois validé, c'est gravé.

BASE (NoSQL distribué)

  • Basically Available — priorité à la disponibilité.
  • Soft state — l'état peut changer sans écriture.
  • Eventual consistency — cohérence à terme.

Le choix découle du théorème CAP (chapitre 8) : dans un système distribué, on ne peut pas tout avoir.

Réplication

Répliquer, c'est copier la base sur plusieurs serveurs. Deux bénéfices : la disponibilité (une copie tombe, une autre prend le relais) et la scalabilité en lecture (on répartit les lectures sur les réplicas). Schéma primary / replicas :

App
Primaryécritures
Replicaslectures
  • Écritures → primary, lectures → replicas. Comme la plupart des apps lisent bien plus qu'elles n'écrivent (souvent 80–90 % de lectures), on scale énormément ainsi.
  • Réplication asynchrone — rapide, mais un réplica peut être légèrement en retard (replication lag → lecture d'une donnée périmée).
  • Réplication synchrone — cohérente, mais plus lente (on attend les réplicas).
  • Failover — si le primary tombe, un réplica est promu automatiquement.

Partitionnement & sharding

Quand une seule base ne suffit plus (trop de données, trop d'écritures), on la découpe. Le sharding répartit les lignes sur plusieurs bases selon une clé de partition (ex. l'ID utilisateur). Chaque shard ne gère qu'une portion des données.

App
hash(user_id)
Shard Ausers 0–9M
Shard Busers 9–18M
Shard Cusers 18M+
Le sharding coûte cher — en dernier recours

Il introduit de vrais problèmes : les JOIN entre shards deviennent difficiles, les hotspots (une clé mal choisie surcharge un shard), et le rebalancing est pénible. Ordre des leviers : optimiser les requêtes & index → cache → read replicas → puis seulement sharding.

Bonnes pratiques

Le mémo base de données
  • SQL par défaut — passez au NoSQL pour un besoin précis, pas par hype.
  • Indexer les bonnes colonnes — celles des WHERE/JOIN, pas toutes.
  • Read replicas avant sharding — la plupart des charges sont dominées par les lectures.
  • Choisir la clé de partition avec soin — c'est irréversible et source de hotspots.
  • Toujours sauvegarder & tester la restauration — la durabilité ne se présume pas.

On sait faire tenir la base. Mais la meilleure requête reste celle qu'on n'exécute pas : place au chapitre Caching.

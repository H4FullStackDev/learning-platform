02 System Design Débutant

Les briques du web

Avant d'assembler un système, il faut connaître ses pièces : client/serveur, DNS, HTTP, API et bases de données. Ce chapitre pose le vocabulaire commun de tout le module.

Pourquoi ce chapitre. On ne peut pas concevoir avec des briques qu'on ne comprend pas. Ici, on suit le trajet d'une requête — de la barre d'adresse jusqu'à la base de données — et on nomme chaque étape. Rien de neuf si vous développez déjà : on va vite, mais on fixe le socle.

Client & serveur

Le web repose sur un modèle requête / réponse. Un client (navigateur, app mobile) envoie une requête ; un serveur la traite et renvoie une réponse. Le client ne sait rien de ce qui se passe derrière — c'est justement ce qui nous laisse libres de concevoir l'arrière-boutique.

DNS : du nom à l'adresse

On tape exemple.com, mais les machines communiquent par adresses IP. Le DNS (Domain Name System) est l'annuaire du web : il traduit un nom de domaine en IP. Un resolver parcourt la hiérarchie DNS, puis met le résultat en cache (d'où la rapidité des visites suivantes).

Navigateur
exemple.com ?
ResolverDNS récursif
Racine → TLD.com
Serveur autoritaire→ 93.184.216.34

Le resolver interroge la racine, puis le TLD (.com), puis le serveur autoritaire du domaine, obtient l'IP, la renvoie au navigateur et la garde en cache (selon le TTL de l'enregistrement).

HTTP : le langage du web

Une fois l'IP connue, le navigateur parle HTTP (HTTPS = HTTP + chiffrement TLS). C'est un protocole sans état (stateless) : chaque requête est indépendante, le serveur ne « se souvient » de rien entre deux appels. Cette propriété est fondamentale — c'est elle qui permettra plus tard de multiplier les serveurs (chapitre suivant).

Idempotent = rejouer la requête donne le même résultat. C'est crucial pour les retries en cas de panne réseau (on y reviendra avec la résilience).

Les API REST

Une API expose les fonctions d'un service. Le style REST organise tout autour de ressources (des noms : /users, /orders) qu'on manipule avec les méthodes HTTP. C'est lisible, cacheable et sans état :

requête & réponse REST
GET /api/users/42 HTTP/1.1
Host: api.exemple.com
Accept: application/json
Authorization: Bearer <token>

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 42, "name": "Alice", "email": "alice@exemple.com" }

Autres styles qu'on comparera au chapitre Communication entre services : gRPC (rapide, binaire, entre services) et GraphQL (le client choisit les champs).

Les bases de données (survol)

Le serveur a besoin de persister les données. Deux grandes familles, qu'on approfondira au chapitre suivant du tier intermédiaire :

SQL (relationnel)

Données structurées en tables, schéma strict, requêtes puissantes (JOIN), garanties ACID. Ex. : PostgreSQL, MySQL. Idéal quand les relations & la cohérence comptent.

NoSQL

Schéma souple, pensé pour l'échelle horizontale (documents, clé-valeur, colonnes, graphes). Ex. : MongoDB, Redis, Cassandra. Idéal pour de gros volumes & un débit élevé.

Le modèle multi-tier

En assemblant ces briques, on obtient l'architecture web classique en couches (tiers). Chaque couche a un rôle et peut évoluer indépendamment — c'est le squelette qu'on va faire grandir dans tout le module :

À retenir
  • Le DNS se cache — d'où l'importance des TTL (et pourquoi un changement d'IP met du temps à se propager).
  • HTTP est sans état — la clé qui rendra le scaling horizontal possible.
  • REST = ressources + méthodes HTTP — simple, cacheable, universel.
  • Le multi-tier découple — chaque couche (LB, app, cache, base) évolue à son rythme.

On connaît les briques et le squelette. La vraie question du System Design arrive : comment faire tenir ce squelette quand le trafic explose ? Direction le chapitre Scalabilité & performance : les bases.

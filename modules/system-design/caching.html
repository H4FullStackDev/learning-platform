05 System Design Intermédiaire

Caching

Le levier de performance le plus rentable : garder à portée de main ce qui coûte cher à recalculer. Les couches, les stratégies — et le vrai problème, l'invalidation.

L'idée. Un cache stocke temporairement un résultat coûteux (requête, calcul, page) dans un espace rapide, pour le resservir sans le refaire. C'est souvent le moyen le moins cher de diviser la latence et la charge par 10 — à condition de maîtriser la fraîcheur des données.

Les couches de cache

Le cache est partout sur le trajet d'une requête. Chaque couche absorbe une partie de la charge avant la suivante :

Navigateurcache client
CDNcache edge
Rediscache applicatif
Base+ cache interne
  • Client — le navigateur cache les assets (en-têtes Cache-Control).
  • CDN — cache le statique au plus près de l'utilisateur (chapitre 3).
  • Applicatif — Redis/Memcached en mémoire : résultats de requêtes, sessions, compteurs.
  • Base — la base elle-même cache ses pages fréquentes en RAM.

Les stratégies de cache

La plus courante, cache-aside, en quelques lignes :

cache-aside (Node.js)
async function getProduit(id) {
  const cle = `produit:${id}`;
  const cache = await redis.get(cle);
  if (cache) return JSON.parse(cache);            // HIT : la base n'est pas touchée

  const produit = await db.query('SELECT * FROM produits WHERE id = $1', [id]);
  await redis.set(cle, JSON.stringify(produit), 'EX', 300);   // MISS : on remplit (TTL 5 min)
  return produit;
}

Éviction & expiration

La mémoire est limitée : quand le cache est plein, il faut virer quelque chose. Deux mécanismes complémentaires :

  • TTL (Time To Live) — chaque entrée expire au bout d'un délai. Simple et efficace pour borner la péremption.
  • Politique d'éviction — quand c'est plein : LRU (on vire le moins récemment utilisé, le défaut de Redis), LFU (le moins fréquent), FIFO.

L'invalidation : le vrai problème

« Il n'y a que deux choses difficiles en informatique : l'invalidation de cache et nommer les choses. » — Phil Karlton

Un cache sert des données potentiellement périmées. Tout l'art est de décider quand rafraîchir :

  • Expiration (TTL) — la donnée devient stale après N secondes. Simple, mais fenêtre de péremption.
  • Invalidation à l'écriture — on supprime/met à jour l'entrée dès que la source change. Précis, mais il faut penser à tous les endroits.
  • Versionnement de clé — la clé inclut une version (produit:42:v7) ; changer la version « invalide » sans supprimer.
Deux pièges classiques

Cache stampede (thundering herd) — une clé populaire expire, et 10 000 requêtes frappent la base en même temps pour la recalculer. Parades : verrou de recalcul, expiration « jitterée », rafraîchissement anticipé.
Cache penetration — des requêtes pour des clés inexistantes traversent le cache à chaque fois. Parade : cacher aussi les « non trouvé » (avec un TTL court).

Bonnes pratiques

Le mémo cache
  • Cacher ce qui est cher & peu changeant — profils, catalogues, agrégats, pas les données ultra-volatiles.
  • Toujours un TTL — jamais de cache éternel ; il borne l'incohérence.
  • Choisir sa tolérance à la péremption — quelques secondes de retard sur un compteur de likes ? oui. Sur un solde bancaire ? non.
  • Mesurer le taux de hit — un cache à faible hit-rate coûte sans rien rapporter.
  • Prévoir stampede & penetration — surtout sur les clés populaires.

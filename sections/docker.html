04 Module DevOps

Conteneurisation (Docker)

Empaqueter une application et toutes ses dépendances dans une image portable, reproductible et légère. Dockerfile multi-stage, Docker Compose multi-services, et les optimisations qui font la différence en production.

Le problème résolu. Le conteneur met fin au « ça marche sur ma machine » : l'application et son environnement (runtime, libs, config) voyagent ensemble dans une unité isolée et identique du poste du développeur jusqu'à la production. C'est l'artifact immuable du chapitre CI, prêt à être déployé.

Concepts clés

  • Image — un modèle en lecture seule, empilé en couches, contenant tout le nécessaire pour lancer l'app. Immuable et versionnée par un tag.
  • Conteneur — une instance en cours d'exécution d'une image, avec une fine couche inscriptible par-dessus. Éphémère et jetable.
  • Layer (couche) — chaque instruction du Dockerfile crée une couche, mise en cache et partagée entre images. C'est la clé de l'optimisation.
  • Registry (registre) — l'entrepôt d'images (Docker Hub, GHCR, ECR…). On y push une image buildée, on la pull pour la déployer.

Une image se lit de bas en haut : chaque instruction empile une couche immuable, et le conteneur n'ajoute qu'une couche inscriptible au sommet.

Le Dockerfile en détail

Chaque instruction pilote la construction de l'image. Les principales :

InstructionRôle
FROMImage de base ; démarre aussi une étape (nommable avec AS).
WORKDIRDéfinit (et crée) le répertoire de travail des instructions suivantes.
COPYCopie des fichiers du contexte de build vers l'image. (ADD fait plus, mais on préfère COPY.)
RUNExécute une commande pendant le build — crée une nouvelle couche.
ENVDéfinit une variable d'environnement persistante dans l'image.
EXPOSEDocumente le port écouté (informatif ; n'ouvre rien tout seul).
USERFixe l'utilisateur qui exécutera les instructions/le process suivants.
CMDCommande par défaut du conteneur — surchargeable au docker run.
ENTRYPOINTExécutable fixe du conteneur ; CMD lui fournit alors les arguments par défaut.
CMD vs ENTRYPOINT

Règle simple : ENTRYPOINT = quoi exécuter (l'exécutable, non surchargé), CMD = les arguments par défaut (facilement surchargés). Pour une app web, un simple CMD ["node","dist/server.js"] suffit ; ENTRYPOINT brille pour packager un outil CLI.

Multi-stage build — l'exemple complet

Le multi-stage build sépare l'environnement de construction (SDK, dev dependencies, outils de build — volumineux) de l'image finale de production (le strict minimum pour tourner). On ne copie dans l'image finale que l'artefact buildé.

Dockerfile
# syntax=docker/dockerfile:1

# ===== Étape 1 : BUILD (lourde, jetable) =====
FROM node:20-alpine AS builder        # image de base légère + alias d'étape "builder"
WORKDIR /app                          # répertoire de travail (créé si absent)

# Copier D'ABORD les manifestes -> la couche des dépendances est mise en cache
COPY package.json package-lock.json ./
RUN npm ci                            # install déterministe (dev deps incluses ici)

# Puis le code source, et on build
COPY . .
RUN npm run build                     # produit /app/dist

# ===== Étape 2 : RUNTIME (minimale, en prod) =====
FROM node:20-alpine AS runtime        # on repart d'une base propre et minimale
ENV NODE_ENV=production
WORKDIR /app

# N'installer QUE les dépendances de production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# Récupérer UNIQUEMENT l'artefact buildé depuis l'étape "builder"
COPY --from=builder /app/dist ./dist

# Sécurité : créer et utiliser un utilisateur non-root
RUN addgroup -S app && adduser -S app -G app
USER app

EXPOSE 3000                           # documente le port applicatif
CMD ["node", "dist/server.js"]        # process par défaut du conteneur

Résultat : l'image finale ne contient ni le code source, ni les outils de build, ni les dev dependencies — juste le runtime, les deps de prod et dist/.

Bonnes pratiques du Dockerfile

  • Ordre des couches pour le cache — copier package*.json et installer les dépendances avant de copier le code. Tant que le lockfile ne change pas, Docker réutilise la couche des deps (l'étape la plus lente).
  • Image de base légère — alpine (~5 MB) plutôt que la variante complète ; distroless pour aller plus loin (ni shell, ni gestionnaire de paquets → surface d'attaque minimale).
  • Utilisateur non-root — ne jamais tourner en root dans le conteneur (USER app).
  • Une image mince — nettoyer les caches (npm cache clean), combiner les RUN, ne rien installer d'inutile.

.dockerignore

Comme .gitignore, il exclut des fichiers du contexte de build : builds plus rapides, images plus propres, et surtout on évite de copier des secrets ou node_modules.

Docker Compose — orchestrer plusieurs services

Une vraie application, c'est rarement un seul conteneur. Docker Compose décrit, dans un seul fichier YAML, un ensemble de services qui démarrent ensemble, communiquent sur un réseau interne et persistent leurs données. Exemple : app Node + Postgres + Redis + reverse proxy nginx.

Seul nginx est exposé à l'extérieur (port 80). Les autres services ne sont joignables que sur le réseau interne, par leur nom (app, db, cache) — le DNS intégré de Compose.

docker-compose.yml
# Un réseau par défaut est créé automatiquement : les services
# s'y trouvent et se joignent par leur nom (résolution DNS interne).
services:

  # ---------- Application ----------
  app:
    build: .                          # construit l'image depuis le Dockerfile local
    environment:
      NODE_ENV: production
      # les services se contactent par leur nom : db, cache
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
      REDIS_URL: redis://cache:6379
    depends_on:
      db:
        condition: service_healthy    # attend que Postgres soit "healthy"
      cache:
        condition: service_started
    expose: ["3000"]                  # visible seulement en interne (pas publié)
    restart: unless-stopped           # relance auto sauf arrêt manuel

  # ---------- Base de données ----------
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}   # injecté depuis le fichier .env
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data   # persistance des données
    healthcheck:                          # sonde de disponibilité
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  # ---------- Cache ----------
  cache:
    image: redis:7-alpine
    command: ["redis-server", "--save", "60", "1"]  # snapshot toutes les 60s
    volumes:
      - redisdata:/data
    restart: unless-stopped

  # ---------- Reverse proxy ----------
  proxy:
    image: nginx:1.27-alpine
    ports:
      - "80:80"                        # SEUL service publié vers l'extérieur
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro   # config en lecture seule
    depends_on: [ app ]
    restart: unless-stopped

# Volumes nommés : les données survivent au recréement des conteneurs
volumes:
  pgdata:
  redisdata:
nginx.conf
server {
    listen 80;

    location / {
        proxy_pass http://app:3000;         # "app" = nom du service Compose
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

On lance le tout avec docker compose up -d --build, et on suit les logs avec docker compose logs -f app.

Bonnes pratiques

Images de production : le mémo
  • Scanner les vulnérabilités — passer chaque image au crible avec Trivy (ou Grype) dans la CI, avant tout push. On casse le build si des CVE HIGH/CRITICAL sont détectées.
  • Tagger explicitement — jamais latest en prod — latest est un pointeur mouvant et non reproductible. Utiliser le SHA du commit ou une version (1.4.2), pour savoir exactement ce qui tourne et pouvoir rollback.
  • Registre privé — pousser vers un registre contrôlé (GHCR, ECR, GitLab Registry, Harbor) avec authentification, plutôt que de dépendre d'images publiques non maîtrisées.
  • Images minimales — alpine/distroless + multi-stage + non-root = surface d'attaque réduite.
bash
# Scanner l'image avant de la pousser (échoue si CVE HIGH/CRITICAL)
trivy image --severity HIGH,CRITICAL --exit-code 1 registre.exemple.com/app:$(git rev-parse --short HEAD)

# Tagger avec le SHA du commit (reproductible) plutôt que "latest"
docker build -t registre.exemple.com/app:$(git rev-parse --short HEAD) .
docker push registre.exemple.com/app:$(git rev-parse --short HEAD)

L'image validée et scannée est prête. Au chapitre suivant, Kubernetes prend le relais pour l'exécuter, la scaler et la maintenir en vie à grande échelle.

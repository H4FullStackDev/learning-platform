06 Module DevOps

Infrastructure as Code (Terraform)

Décrire l'infrastructure comme du code : déclaratif, versionné, reproductible. Concepts Terraform un par un, workflow complet, et un exemple concret de bout en bout sur DigitalOcean (VPC, droplet, base managée, load balancer).

L'idée. Plutôt que de cliquer dans une console cloud (irreproductible, non tracé), on décrit l'infrastructure voulue dans des fichiers texte versionnés dans Git. Un outil se charge de créer, modifier ou détruire les ressources pour atteindre cet état. Résultat : une infra reproductible, auditée et revue en Pull Request, exactement comme du code applicatif.

Qu'est-ce que l'Infrastructure as Code ?

L'IaC gère le provisioning de l'infrastructure via des fichiers de définition lisibles par la machine. La distinction fondamentale est déclaratif vs impératif :

Impératif

On décrit les étapes pour arriver au résultat (« crée un serveur, puis installe X, puis ouvre le port 80 »). Fragile : rejouer le script sur un état différent peut échouer ou dupliquer.

Déclaratif (Terraform)

On décrit l'état désiré (« je veux 1 VPC, 1 droplet, 1 base »). L'outil calcule le diff entre le réel et le désiré, et n'applique que ce qui manque. Idempotent par nature.

  • Reproductibilité — le même code recrée une infra identique en dev, staging et prod.
  • Versioning — l'historique de l'infra vit dans Git : qui a changé quoi, quand, et pourquoi (via la PR).
  • Revue & sécurité — chaque changement passe par un plan revu avant d'être appliqué.
  • Récupération — en cas de sinistre, on reprovisionne tout à partir du code.

Les concepts Terraform

Providers

Un provider est le plugin qui traduit le code Terraform en appels d'API vers une plateforme (DigitalOcean, AWS, Kubernetes…). On déclare ceux dont on a besoin, avec une contrainte de version :

providers.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    digitalocean = {
      source  = "digitalocean/digitalocean"
      version = "~> 2.40"          # accepte 2.40.x, refuse 3.0
    }
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

# Configuration de chaque provider
provider "digitalocean" {
  token = var.do_token             # jamais en dur : via variable sensible
}

provider "aws" {
  region = "eu-west-1"
}

Resources

La resource est la brique de base : elle représente un objet d'infrastructure. Syntaxe : resource "<type>" "<nom_local>" { … }. On référence une ressource ailleurs via <type>.<nom>.<attribut>.

exemple de resource
resource "digitalocean_droplet" "web" {
  name   = "web-1"
  image  = "ubuntu-24-04-x64"
  size   = "s-1vcpu-1gb"
  region = "fra1"
}

# Référence : digitalocean_droplet.web.ipv4_address

Variables & outputs

Les variables paramètrent le code (entrées) ; les outputs exposent des valeurs calculées (sorties), utiles pour l'affichage ou pour connecter des modules.

variables.tf
variable "region" {
  description = "Région de déploiement"
  type        = string
  default     = "fra1"
}

variable "do_token" {
  description = "Token API DigitalOcean"
  type        = string
  sensitive   = true               # masqué dans les logs et le plan
}
outputs.tf
output "droplet_ip" {
  description = "IP publique du droplet"
  value       = digitalocean_droplet.web.ipv4_address
}

State (terraform.tfstate)

Terraform garde une trace de tout ce qu'il gère dans un fichier de state (terraform.tfstate) : la correspondance entre votre code et les ressources réelles du cloud. C'est ce qui lui permet de calculer les diffs. Ce fichier contient des données sensibles (souvent des secrets en clair) — il ne doit jamais être commité.

En équipe, on le stocke sur un backend distant, partagé et verrouillé (state locking) pour éviter deux apply simultanés qui corrompraient l'infra. Exemple classique AWS : bucket S3 (stockage) + table DynamoDB (verrou).

backend.tf
terraform {
  backend "s3" {
    bucket         = "mon-org-tfstate"
    key            = "digitalocean/prod/terraform.tfstate"
    region         = "eu-west-1"
    dynamodb_table = "terraform-locks"   # verrou : un seul apply à la fois
    encrypt        = true                # state chiffré at-rest
  }
}
# Alternative clé en main : Terraform Cloud / HCP (state + lock + exécution gérés)

Modules

Un module est un ensemble de fichiers .tf réutilisable et paramétrable — l'équivalent d'une fonction pour l'infra. On structure un projet en modules par domaine (réseau, app…) appelés depuis chaque environnement.

arborescence
infra/
├── modules/
│   ├── network/            # VPC, firewall
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── app/                # droplet + load balancer
│       └── ...
└── environments/
    ├── dev/
    │   ├── main.tf         # appelle les modules avec les valeurs "dev"
    │   └── terraform.tfvars
    └── prod/
        ├── main.tf
        └── terraform.tfvars
environments/prod/main.tf (extrait)
module "network" {
  source      = "../../modules/network"   # chemin (ou registry, ou git)
  environment = "prod"
  region      = var.region
}

module "app" {
  source     = "../../modules/app"
  vpc_id     = module.network.vpc_id       # sortie d'un module -> entrée d'un autre
  region     = var.region
}

Workspaces

Les workspaces permettent de gérer plusieurs états (dev/staging/prod) avec le même code, chacun ayant son propre state isolé. On référence terraform.workspace pour nommer les ressources par environnement.

bash
terraform workspace new staging      # crée un environnement isolé
terraform workspace select prod      # bascule dessus
terraform workspace list             # * indique le workspace actif

# Dans le code : name = "web-${terraform.workspace}"  ->  web-prod, web-staging...
Workspaces ou dossiers par environnement ?

Les workspaces sont pratiques pour des environnements quasi identiques. Dès que les configs divergent sérieusement (tailles, options, comptes cloud distincts), beaucoup d'équipes préfèrent un dossier par environnement (comme l'arborescence ci-dessus) : plus explicite et moins risqué qu'un mauvais workspace select avant un apply en prod.

Le workflow Terraform

Le cycle de vie tient en quelques commandes. On ne saute jamais l'étape plan avant un apply.

inittélécharge providers + backend
plancalcule le diff
applycrée / met à jour
☁️ infra vivante
destroydétruit tout
bash
terraform init          # initialise le dossier : providers + backend
terraform fmt           # formate le code (canonique)
terraform validate      # vérifie la syntaxe et la cohérence
terraform plan          # montre CE QUI VA changer -> à revoir absolument
terraform apply         # applique après confirmation (ou -auto-approve en CI)
terraform destroy       # détruit l'ensemble des ressources gérées

main.tf

main.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    digitalocean = {
      source  = "digitalocean/digitalocean"
      version = "~> 2.40"
    }
  }
}

provider "digitalocean" {
  token = var.do_token
}

# --- Réseau privé isolé ---
resource "digitalocean_vpc" "main" {
  name     = "${var.environment}-vpc"
  region   = var.region
  ip_range = "10.10.0.0/16"
}

# --- Serveur applicatif (VM) ---
resource "digitalocean_droplet" "web" {
  name     = "${var.environment}-web"
  image    = "ubuntu-24-04-x64"
  size     = var.droplet_size
  region   = var.region
  vpc_uuid = digitalocean_vpc.main.id       # rattaché au VPC
  ssh_keys = [var.ssh_key_fingerprint]      # accès SSH par clé publique
  tags     = [var.environment, "web"]
}

# --- Base de données PostgreSQL managée ---
resource "digitalocean_database_cluster" "postgres" {
  name                 = "${var.environment}-pg"
  engine               = "pg"
  version              = "16"
  size                 = var.db_size
  region               = var.region
  node_count           = 1
  private_network_uuid = digitalocean_vpc.main.id   # accessible en privé uniquement
}

# --- Load balancer public devant le droplet ---
resource "digitalocean_loadbalancer" "public" {
  name     = "${var.environment}-lb"
  region   = var.region
  vpc_uuid = digitalocean_vpc.main.id

  forwarding_rule {
    entry_port      = 80          # port exposé à Internet
    entry_protocol  = "http"
    target_port     = 80          # port du droplet
    target_protocol = "http"
  }

  healthcheck {
    port     = 80
    protocol = "http"
    path     = "/healthz"         # le LB retire un droplet non sain
  }

  droplet_ids = [digitalocean_droplet.web.id]   # backends du LB
}

Injecter le token sans le committer

On ne met jamais le token dans le code. On l'expose par variable d'environnement : export TF_VAR_do_token="dop_v1_…" — Terraform mappe automatiquement TF_VAR_<nom> vers var.<nom>. Puis : terraform plan → terraform apply.

Terraform et Ansible sont souvent complémentaires : Terraform crée les serveurs, Ansible les configure ensuite.

Bonnes pratiques

À ne jamais faire

Ne jamais committer le terraform.tfstate (il contient des secrets en clair) ni les tokens/mots de passe. Un .gitignore minimal :

*.tfstate
*.tfstate.*
.terraform/
*.tfvars          # sauf variables non sensibles versionnées volontairement
override.tf
crash.log
Le mémo IaC
  • fmt + validate en CI — un pipeline qui vérifie le format et la validité à chaque PR (plus tflint / checkov pour le lint & la sécurité).
  • Revue du plan avant apply — publier la sortie de terraform plan dans la PR ; on n'applique qu'après relecture humaine.
  • State distant & verrouillé — S3+DynamoDB ou Terraform Cloud : état partagé, chiffré, avec verrou pour empêcher les apply concurrents.
  • Secrets hors du code — sensitive = true, variables via TF_VAR_* ou Vault, jamais en dur.
  • Versions épinglées — contraindre les versions de Terraform et des providers pour des plans reproductibles.

07 Module DevOps

GitOps & Déploiement Continu (CD)

Faire de Git la source de vérité unique de l'état désiré — infra et applications. Un agent dans le cluster réconcilie en continu. Push vs pull, ArgoCD, stratégies de déploiement, et le rollback réduit à un simple git revert.

Le principe. En GitOps, on ne pousse plus les changements vers le cluster : on décrit l'état voulu dans Git, et un agent installé dans le cluster tire cet état et le fait converger en permanence. Git devient l'unique source de vérité — pour le déploiement des apps comme pour la configuration de l'infra.

Qu'est-ce que le GitOps ?

Le GitOps applique les pratiques Git (branches, PR, revue, historique) au déploiement et à l'opération. Tout l'état désiré — manifests Kubernetes, charts Helm, config Terraform — vit dans des dépôts Git. Un opérateur de réconciliation (ArgoCD, Flux) surveille ces dépôts et aligne le cluster sur ce qui y est déclaré. Concrètement :

  • Le déploiement = un commit/merge dans le repo de config. Pas de kubectl apply manuel.
  • Le rollback = un git revert. On revient à un état connu et tracé.
  • L'audit est gratuit : l'historique Git répond à « qui a déployé quoi, quand ».

Pourquoi le pull est plus sûr

En push, le pipeline détient des identifiants d'admin du cluster — une CI compromise compromet la prod. En pull, aucun secret cluster ne sort du cluster : l'agent lit Git (droits en lecture) et applique en interne. La surface d'attaque est nettement réduite, et le cluster s'auto-corrige en continu.

Les 4 principes du GitOps

1

Déclaratif

L'état désiré du système est décrit de façon déclarative (YAML, HCL).

2

Versionné & immuable

Cet état est stocké dans Git : versionné, auditable, avec un historique complet.

3

Tiré automatiquement

Des agents appliquent automatiquement l'état désiré depuis la source.

4

Réconcilié en continu

Les agents détectent et corrigent en permanence les écarts (drift).

ArgoCD en détail

ArgoCD est un contrôleur GitOps déclaratif pour Kubernetes, doté d'une interface web riche. Il compare en continu l'état désiré (Git) à l'état réel (cluster) et synchronise.

Repo Gitmanifests / Helm

Ressources K8sétat réel

Les objets d'ArgoCD

  • Application (CRD) — l'objet central : il lie une source (repo + chemin + révision) à une destination (cluster + namespace), avec une sync policy.
  • ApplicationSet — génère automatiquement de multiples Applications à partir d'un gabarit (une par environnement, par cluster ou par dossier). Idéal pour éviter la duplication.
  • Sync policy — manuelle (on clique/valide) ou automated (auto-sync), avec prune et selfHeal.

Manifest Application — complet et commenté

argocd/applications/web-prod.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-prod
  namespace: argocd                 # ArgoCD vit dans son propre namespace
spec:
  project: default

  # --- SOURCE : où est l'état désiré ---
  source:
    repoURL: https://github.com/acme/config-repo.git
    targetRevision: main            # branche/tag suivi
    path: apps/web/overlays/prod    # dossier des manifests (Kustomize ici)

  # --- DESTINATION : où déployer ---
  destination:
    server: https://kubernetes.default.svc   # le cluster local
    namespace: prod

  # --- POLITIQUE DE SYNCHRONISATION ---
  syncPolicy:
    automated:
      prune: true                   # supprime les ressources retirées du Git
      selfHeal: true                # annule tout changement manuel (anti-drift)
    syncOptions:
      - CreateNamespace=true        # crée le namespace s'il n'existe pas
    retry:
      limit: 3                      # réessaie en cas d'échec de sync
      backoff:
        duration: 10s
        maxDuration: 3m

Drift detection & auto-sync

ArgoCD calcule en continu un statut de synchronisation. Si quelqu'un modifie le cluster à la main (kubectl edit), l'état réel diverge du Git : l'Application passe OutOfSync — c'est le drift. Deux comportements :

  • Auto-sync (automated) — ArgoCD réapplique automatiquement le Git dès qu'un écart apparaît.
  • Self-heal (selfHeal: true) — tout changement manuel est immédiatement écrasé par l'état déclaré dans Git. Le Git gagne, toujours.

Stratégies de déploiement

Le GitOps orchestre le déploiement, mais la manière de basculer d'une version à l'autre reste à choisir. Trois stratégies :

Rolling update

Les pods v1 sont remplacés progressivement par des v2, un lot à la fois. Zéro downtime, pas de coût d'infra doublé. Stratégie par défaut de Kubernetes.

100 % v2
Blue-Green

Deux environnements complets coexistent. Blue sert le trafic pendant que Green (la v2) est déployé et testé. On bascule tout le trafic d'un coup. Rollback instantané : on rebascule sur Blue. Coût : infra doublée le temps de la bascule.

Canary

On expose la v2 à une petite fraction du trafic, on surveille les métriques (erreurs, latence), puis on augmente progressivement. On coupe au moindre problème. Automatisable avec Argo Rollouts ou Flagger.

Structure d'un repo GitOps

Bonne pratique : séparer le repo applicatif (code source + CI qui build l'image) du repo de configuration (manifests que l'opérateur GitOps surveille). La CI met à jour le tag d'image dans le repo de config ; ArgoCD déploie. Les responsabilités restent découplées.

config-repo (surveillé par ArgoCD)
config-repo/
├── apps/
│   └── web/
│       ├── base/                    # manifests communs (Kustomize)
│       │   ├── deployment.yaml
│       │   ├── service.yaml
│       │   └── kustomization.yaml
│       └── overlays/                # spécificités par environnement
│           ├── staging/
│           │   ├── kustomization.yaml
│           │   └── replicas-patch.yaml   # ex : 1 replica
│           └── prod/
│               ├── kustomization.yaml
│               └── replicas-patch.yaml   # ex : 3 replicas + image tag
└── argocd/
    └── applications/
        ├── web-staging.yaml         # Application ArgoCD (pointe overlays/staging)
        └── web-prod.yaml            # Application ArgoCD (pointe overlays/prod)

Le flux complet : git push du code → la CI build & scanne l'image (ch.3-4) → la CI bump le tag d'image dans config-repo → ArgoCD détecte le commit et synchronise le cluster.

Bonnes pratiques

Le mémo GitOps
  • Jamais de kubectl apply manuel en prod — avec selfHeal, il serait de toute façon écrasé. Tout changement passe par une PR sur le repo de config.
  • Git = source de vérité unique — l'état du cluster doit toujours être déductible du repo. Pas de configuration « cachée » appliquée à la main.
  • Rollback = git revert — pour revenir en arrière, on annule le commit : l'opérateur ramène le cluster à l'état précédent, tracé et reproductible.
  • Repos séparés app / config — la CI n'a pas besoin d'accès au cluster ; elle écrit juste dans le repo de config.
  • Revue obligatoire — protéger le repo de config comme la prod (required reviews, cf. chapitre Git).

Le déploiement est désormais automatique, traçable et réversible. Reste à voir ce qui tourne en production : c'est l'objet du chapitre Monitoring & Observabilité.

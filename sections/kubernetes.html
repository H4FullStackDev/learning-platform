05 Module DevOps

Orchestration (Kubernetes)

Faire tourner des conteneurs à grande échelle : les planifier, les scaler, les guérir automatiquement et les exposer. Architecture, objets fondamentaux avec manifests réels, Helm, et les bonnes pratiques de production.

Pourquoi orchestrer ? Un conteneur seul, c'est simple. Des centaines de conteneurs répartis sur des dizaines de machines, avec du scaling, des mises à jour sans coupure, de l'auto-réparation et du réseau interne — c'est un problème d'orchestration. Kubernetes (K8s) est le standard de facto qui le résout de façon déclarative : on décrit l'état désiré, il s'occupe de l'atteindre et de le maintenir.

Architecture de Kubernetes

Un cluster se divise en deux plans : le control plane (le cerveau, qui prend les décisions) et les worker nodes (les machines qui exécutent réellement les conteneurs). L'utilisateur ne parle qu'à l'API Server, via kubectl ou un outil GitOps.

Le principe central est la réconciliation : les controllers comparent en continu l'état réel à l'état désiré (stocké dans etcd) et corrigent l'écart. Un pod meurt ? Un controller en recrée un. C'est ce qui rend Kubernetes auto-réparateur.

Les objets Kubernetes

Tout dans K8s est un objet décrit en YAML et soumis à l'API. Passons-les en revue, du plus bas niveau au plus haut.

Pod

Le Pod est la plus petite unité déployable : un ou plusieurs conteneurs qui partagent le réseau (même IP) et le stockage. On en crée rarement un directement — on laisse un Deployment le gérer.

pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web                     # étiquette qui servira aux Services/selectors
spec:
  containers:
    - name: web
      image: registre.exemple.com/app:1.4.2   # tag explicite (jamais latest)
      ports:
        - containerPort: 3000    # port écouté par le conteneur

Deployment

Le Deployment est l'objet que l'on manipule au quotidien. Il gère un ReplicaSet qui maintient un nombre de replicas, assure l'auto-réparation, et orchestre les rolling updates (mise à jour progressive, sans coupure). C'est aussi ici qu'on déclare resources et probes.

deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3                        # 3 pods identiques maintenus en permanence
  selector:
    matchLabels:
      app: web                       # ce Deployment gère les pods app=web
  strategy:
    type: RollingUpdate              # remplacement progressif -> zéro downtime
    rollingUpdate:
      maxSurge: 1                    # au plus 1 pod EN PLUS pendant la MAJ
      maxUnavailable: 0              # aucun pod indisponible pendant la MAJ
  template:                          # gabarit des pods créés
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: registre.exemple.com/app:1.4.2
          ports:
            - containerPort: 3000
          resources:                 # requests = réservé, limits = plafond dur
            requests:
              cpu: "100m"            # 0,1 cœur garanti
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "256Mi"        # dépassement mémoire -> OOMKilled
          readinessProbe:            # "prêt à recevoir du trafic ?"
            httpGet: { path: /healthz, port: 3000 }
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:             # "encore vivant ?" sinon redémarrage
            httpGet: { path: /healthz, port: 3000 }
            initialDelaySeconds: 15
            periodSeconds: 20
Rolling update, concrètement

Avec maxSurge: 1 / maxUnavailable: 0, K8s crée un nouveau pod (v2), attend qu'il soit ready, supprime un ancien (v1), et recommence — jusqu'à ce que tous les pods soient en v2. La capacité de service ne descend jamais sous le seuil. En cas de problème : kubectl rollout undo deployment/web revient à la version précédente.

Service

Les pods sont éphémères : leur IP change à chaque recréation. Le Service fournit un point d'accès stable et répartit le trafic sur les pods correspondant à un selector. Trois types selon la portée :

TypePortéeCas d'usage
ClusterIP (défaut)Interne au cluster uniquementCommunication entre services (app → db)
NodePortOuvre un port sur chaque nodeAccès direct simple, dev/test
LoadBalancerProvisionne un load balancer cloud externeExposer un service à Internet (via le cloud)
service.yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP                    # IP virtuelle interne et stable
  selector:
    app: web                         # route vers tous les pods app=web
  ports:
    - port: 80                       # port exposé par le Service
      targetPort: 3000               # port du conteneur cible

Ingress

L'Ingress gère le routage HTTP/HTTPS de niveau 7 : un point d'entrée unique qui route selon le host et le path vers différents Services, avec terminaison TLS. Il nécessite un ingress controller (ex. nginx-ingress) installé dans le cluster.

ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx
  rules:
    - host: app.exemple.com          # routage par nom de domaine
      http:
        paths:
          - path: /                  # le site -> service "web"
            pathType: Prefix
            backend:
              service:
                name: web
                port: { number: 80 }
          - path: /api               # l'API -> service "api"
            pathType: Prefix
            backend:
              service:
                name: api
                port: { number: 80 }
  tls:                               # HTTPS : le certificat vit dans un Secret
    - hosts: [ app.exemple.com ]
      secretName: web-tls

ConfigMap & Secret

On ne code jamais la configuration en dur dans l'image. Le ConfigMap stocke la config non sensible (variables, fichiers), le Secret les données sensibles (mots de passe, tokens, certificats). Attention : un Secret est encodé en base64, pas chiffré — voir l'encart bonnes pratiques.

config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  APP_ENV: production                # config en clair, non sensible
  LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata:
  name: web-secret
type: Opaque
data:
  # base64 (echo -n 'super-secret' | base64) -> encodage, PAS chiffrement
  DB_PASSWORD: c3VwZXItc2VjcmV0

On les injecte ensuite dans les conteneurs du Deployment :

deployment.yaml (extrait)
      containers:
        - name: web
          image: registre.exemple.com/app:1.4.2
          envFrom:
            - configMapRef:
                name: web-config     # injecte APP_ENV et LOG_LEVEL comme variables
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: web-secret   # lit la clé DB_PASSWORD du Secret
                  key: DB_PASSWORD

PersistentVolume & PersistentVolumeClaim

Les conteneurs sont éphémères ; pour persister des données (base de données, uploads) il faut du stockage durable. Le PersistentVolume (PV) est une ressource de stockage du cluster ; le PersistentVolumeClaim (PVC) est une demande de stockage émise par l'app, qui se lie à un PV. En pratique, une StorageClass provisionne le PV dynamiquement.

pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: [ ReadWriteOnce ]     # monté en R/W par un seul node à la fois
  storageClassName: standard         # provisioning dynamique par le cloud
  resources:
    requests:
      storage: 10Gi                  # taille demandée -> un PV de 10Gi est créé

Helm — le gestionnaire de paquets K8s

Écrire et versionner des dizaines de manifests par environnement devient vite ingérable. Helm package tout ça dans un chart réutilisable et paramétrable : les manifests deviennent des templates, alimentés par un fichier de values. Chaque installation est une release versionnée (donc rollback-able).

Structure d'un chart

arborescence
mon-app/
├── Chart.yaml        # métadonnées : nom, version du chart, appVersion
├── values.yaml       # valeurs par défaut (surchargeables à l'install)
├── templates/        # manifests templatisés (Go templating)
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   └── _helpers.tpl  # fonctions/labels réutilisables
└── charts/           # sous-charts (dépendances, ex. postgresql)

Les valeurs par défaut vivent dans values.yaml :

values.yaml
replicaCount: 3
image:
  repository: registre.exemple.com/app
  tag: "1.4.2"
service:
  type: ClusterIP
  port: 80
resources:
  requests: { cpu: 100m, memory: 128Mi }
  limits:   { cpu: 500m, memory: 256Mi }

…et sont injectées dans les templates avec la syntaxe {{ .Values.* }} :

templates/deployment.yaml (extrait)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
bash
# Installer une release nommée "web" dans le namespace prod
helm install web ./mon-app -n prod --create-namespace

# Mettre à jour : nouvelle version d'image, sans toucher au reste
helm upgrade web ./mon-app -n prod --set image.tag=1.4.3

# Revenir à la révision précédente en cas de souci
helm rollback web -n prod

# Inspecter / lister
helm list -n prod
helm get values web -n prod

En pratique, on consomme rarement Kubernetes « à la main » : on utilise une offre managée (GKE, EKS, AKS, DigitalOcean Kubernetes) qui gère le control plane à notre place.

Bonnes pratiques

Le mémo production
  • Resource requests & limits systématiques — les requests guident le scheduler et garantissent une part de CPU/mémoire ; les limits évitent qu'un pod affame ses voisins (noisy neighbor). Sans elles, un cluster devient imprévisible.
  • Liveness & readiness probes — la readiness retire un pod du load balancing tant qu'il n'est pas prêt (démarrage, surcharge) ; la liveness redémarre un pod bloqué. Indispensables pour du zéro downtime.
  • Namespaces pour isoler les environnements — dev, staging, prod dans des namespaces séparés, avec ResourceQuota et RBAC distincts. Isolation logique, quotas, et permissions par équipe.
  • Tout en déclaratif & versionné — les manifests/charts vivent dans Git (cf. chapitre GitOps), jamais de kubectl edit manuel en prod.
Un Secret n'est pas chiffré

Les Secret sont seulement encodés en base64 et lisibles par quiconque a les droits sur le namespace. En production : activer le chiffrement d'etcd at-rest, verrouiller le RBAC, et gérer les secrets avec Sealed Secrets, External Secrets Operator ou Vault — jamais de secret en clair dans Git.

bash — namespaces
# Isoler un environnement complet dans son namespace
kubectl create namespace staging
kubectl apply -f k8s/ -n staging
kubectl get pods -n staging

On sait déployer et opérer des conteneurs à l'échelle. Reste à provisionner l'infrastructure qui héberge ce cluster de façon reproductible : c'est l'objet du chapitre Infrastructure as Code (Terraform).

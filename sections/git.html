02 Module DevOps

Versioning & Collaboration (Git)

Au-delà des commandes : les stratégies de branches, la revue de code, la protection des branches et les conventions de commit qui font tourner une équipe — et alimentent la chaîne CI/CD.

Rappel express. Git est un gestionnaire de versions distribué : chaque clone contient l'historique complet. Un commit est un instantané immuable identifié par un hash ; une branche est un simple pointeur mobile vers un commit ; le merge et le rebase réintègrent un historique dans un autre. On part de là — le vrai sujet, c'est comment on s'organise à plusieurs.

Stratégies de branches

Une branching strategy définit comment le travail circule de l'idée jusqu'à la production. Deux modèles dominent, aux philosophies opposées : Git Flow (beaucoup de branches, releases figées) et Trunk-Based Development (une seule branche vivante, livraison continue).

Git Flow

Formalisé par Vincent Driessen (2010), Git Flow structure le travail autour de deux branches permanentes — main (le code en production, taggé à chaque version) et develop (l'intégration continue des fonctionnalités) — et de trois familles de branches temporaires.

Modèle de branches Git Flow
main — production (taguée) develop — intégration feature/* — fonctionnalités release/* — préparation de version hotfix/* — correctif urgent
Trait plein = création de branche · tirets = fusion / retour vers develop & main.
  • feature/* — part de develop, y retourne une fois la fonctionnalité prête (via PR).
  • release/* — coupée depuis develop pour stabiliser une version (bugfix, doc, bump de version), puis fusionnée dans main et develop.
  • hotfix/* — part de main pour corriger un incident de production, fusionnée dans main (nouveau tag) et develop.
bash
# Feature : on part de develop
git switch develop
git switch -c feature/panier-promo
# ... commits ...
git switch develop
git merge --no-ff feature/panier-promo   # PR + review dans la vraie vie

# Release : figer une version depuis develop
git switch -c release/1.2.0 develop
# bump de version, derniers correctifs...
git switch main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"
git switch develop
git merge --no-ff release/1.2.0

# Hotfix : correctif urgent depuis main
git switch -c hotfix/1.2.1 main
# correction du bug...
git switch main
git merge --no-ff hotfix/1.2.1
git tag -a v1.2.1 -m "Hotfix 1.2.1"
git switch develop
git merge --no-ff hotfix/1.2.1

L'extension git-flow (git flow init, git flow feature start ...) automatise ces étapes, mais comprendre les branches sous-jacentes reste indispensable.

Trunk-Based Development (TBD)

À l'opposé, le TBD n'a qu'une branche vivante : le trunk (main). Chaque développeur y intègre son travail au moins une fois par jour, via des branches ultra-courtes (quelques heures) ou des commits directs. Le code non terminé est masqué derrière des feature flags. C'est le socle de la livraison continue pratiquée par Google, Meta ou la plupart des SaaS.

Modèle Trunk-Based Development
main (trunk) — toujours déployable feature — branches très courtes release — coupée depuis le trunk
Commits fréquents sur le trunk + petites branches (< 1 jour), le code inachevé restant caché derrière des feature flags → déploiement continu.
bash
# Branche courte, synchronisée avec un trunk qui bouge vite
git switch -c fix/tri-produits main
# petit lot cohérent + tests verts
git commit -m "fix(catalog): corrige le tri par prix décroissant"

# rebase pour garder un historique linéaire, puis PR
git fetch origin
git rebase origin/main
git push -u origin fix/tri-produits   # ouvre la PR, CI + review, squash-merge

# Code non terminé ? On le cache derrière un flag, on merge quand même
if (featureFlags.isEnabled("nouveau-checkout")) {
  renderNouveauCheckout();
}

Git Flow ou Trunk-Based : comment choisir ?

CritèreGit FlowTrunk-Based
Branches vivantes2 permanentes + 3 familles temporaires1 seule (le trunk)
Durée de vie des branchesLongue (jours → semaines)Très courte (heures, < 1 jour)
Cadence de releaseVersions planifiées & figéesContinue, plusieurs fois par jour
Feature flagsOptionnelsQuasi indispensables
Conflits de mergeMerges volumineux, risque de « merge hell »Petits & fréquents, peu de conflits
PrérequisDiscipline de branchesCI solide, tests rapides, culture de revue
Idéal pourApps versionnées : mobile (stores), desktop, on-premiseSaaS web, microservices, livraison continue

Git Flow

  • Plusieurs versions à maintenir en parallèle (v1.x et v2.x).
  • Releases contraintes par un tiers (validation d'un store, client on-premise).
  • Équipe nombreuse ou junior : le cadre explicite rassure.
  • Pipeline CD encore immature.

Trunk-Based

  • Objectif de déploiement continu (plusieurs prod/jour).
  • Suite de tests automatisés fiable et rapide.
  • Équipe à l'aise avec les feature flags et la revue continue.
  • Web / API où l'on ne maintient qu'une seule version en prod.
La taille d'équipe n'est pas le seul facteur

On croit souvent « petite équipe → Trunk-Based, grande équipe → Git Flow ». En réalité, Google fait du Trunk-Based avec des dizaines de milliers de développeurs. Le vrai discriminant, c'est votre modèle de release (continue vs versionnée) et la maturité de votre CI. GitHub Flow — trunk + branches courtes + PR — est un excellent compromis pour démarrer.

Pull Requests / Merge Requests

La PR (GitHub) ou MR (GitLab) est l'unité de collaboration : elle propose de fusionner une branche, déclenche la CI et sert de support à la revue de code. Une bonne revue attrape des bugs, diffuse la connaissance et maintient une cohérence d'architecture — à condition d'y mettre les bonnes pratiques.

Côté auteur

  • PR petites et focalisées — une intention par PR. En dessous de ~400 lignes modifiées, la revue est bien plus efficace.
  • Description utile — quoi, pourquoi, comment tester. Lier l'issue/ticket (Closes #142).
  • Auto-revue d'abord — relire son propre diff avant de solliciter les autres.
  • CI verte avant de demander la revue ; utiliser une Draft PR pour un retour précoce.
  • Répondre à tous les commentaires et résoudre les threads plutôt que de les ignorer.

Côté relecteur

  • Réactivité — une PR qui traîne, c'est du contexte perdu et des conflits qui s'accumulent.
  • Distinguer le bloquant du détail — préfixer les remarques mineures par nit:.
  • Critiquer le code, pas la personne — proposer, expliquer le « pourquoi », suggérer des alternatives.
  • Vérifier les tests autant que le code de production.

Protection de branches

Protéger main (et develop) empêche les erreurs coûteuses : push direct, merge sans revue, historique réécrit. On y attache un ensemble de règles vérifiées automatiquement avant tout merge.

  • Required reviews — 1 à 2 approbations ; invalider les approbations si de nouveaux commits arrivent ; exiger l'avis des Code Owners.
  • Required status checks — la CI (build, lint, tests, scan sécurité) doit passer, sur une branche à jour avec la cible.
  • Signed commits — commits signés GPG/SSH pour garantir l'auteur.
  • Linear history — interdire les merge commits (squash ou rebase only) pour un historique lisible.
  • Restrictions — pas de force-push, pas de suppression de branche, résolution des conversations obligatoire.

CODEOWNERS — router la revue automatiquement

Placé à la racine, dans .github/ ou docs/, le fichier CODEOWNERS désigne les relecteurs requis selon les chemins modifiés. GitHub/GitLab les ajoutent automatiquement à la PR.

CODEOWNERS
# Chaque ligne : <motif de chemin>  <propriétaires>
# Le dernier motif qui matche l'emporte.

*                       @acme/maintainers        # par défaut
/api/                   @acme/backend-team
/web/                   @acme/frontend-team
*.tf                    @acme/platform @jdupont   # IaC : équipe + relecteur nommé
/.github/workflows/     @acme/devops
/docs/                  @acme/tech-writers

Configuration en tant que code — .github/settings.yml

Plutôt que de cliquer dans l'UI, on versionne les règles. Exemple avec l'app Repository Settings (format YAML, appliqué automatiquement à chaque push) :

.github/settings.yml
branches:
  - name: main
    protection:
      required_pull_request_reviews:
        required_approving_review_count: 2
        dismiss_stale_reviews: true          # invalide les approbations obsolètes
        require_code_owner_reviews: true     # respecte CODEOWNERS
      required_status_checks:
        strict: true                         # branche à jour obligatoire
        contexts:
          - "ci/build"
          - "ci/test"
          - "security/scan"
      required_signatures: true              # commits signés (GPG/SSH)
      required_linear_history: true          # ni merge commit ni force-push
      enforce_admins: true                   # la règle s'applique aussi aux admins
      restrictions: null                     # personne ne pousse en direct
Équivalents GitLab

Les mêmes garde-fous existent sous d'autres noms : Protected branches + Merge request approval rules (nombre d'approbations, approbateurs de code via CODEOWNERS), Push rules (regex de message, signature GPG requise) et Pipelines must succeed. On les gère dans l'UI ou, mieux, via Terraform (gitlab_branch_protection) — on y reviendra au chapitre Infrastructure as Code.

Activer la signature des commits côté développeur :

bash
# Signature SSH (simple, réutilise votre clé existante)
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true      # signe automatiquement chaque commit

Conventional Commits

Un message de commit libre est du texte perdu. La spécification Conventional Commits impose une structure lisible par un humain et par une machine — ce qui débloque le versioning sémantique et le changelog automatiques.

feat(auth)!: migre le login vers OAuth2
feattype — nature du changement (voir le tableau).
(auth)scope — zone concernée, optionnel (module, package).
!breaking — signale une rupture de compatibilité (équivaut à un footer BREAKING CHANGE:).
migre…description — impératif présent, concis, en minuscules.
TypeQuand l'utiliserImpact SemVer
featNouvelle fonctionnalitéMINOR
fixCorrection de bugPATCH
feat! / BREAKING CHANGERupture de compatibilitéMAJOR
docsDocumentation uniquement—
refactorRefonte sans changer le comportement—
perfAmélioration de performancePATCH
testAjout / correction de tests—
build · ciBuild, dépendances, pipeline CI—
choreTâche de maintenance diverse—
bash
# Simple
git commit -m "fix(catalog): corrige le tri par prix décroissant"

# Avec corps et footer (rupture de compatibilité)
git commit -m "feat(api): passe les dates au format ISO-8601

Uniformise toutes les réponses de l'API sur des timestamps UTC.

BREAKING CHANGE: le champ created_at n'est plus un entier epoch
mais une chaîne ISO-8601. Mettre à jour les clients."

Pourquoi ça compte pour le CI/CD

  • Versioning automatique — un outil comme semantic-release lit les commits depuis le dernier tag et déduit la version : fix → patch, feat → minor, BREAKING CHANGE → major.
  • Changelog généré — le CHANGELOG.md est produit et catégorisé (Features, Bug Fixes…) sans intervention.
  • Déclencheurs CI ciblés — le pipeline peut réagir au type (ex. déployer sur feat/fix, ignorer docs).
  • Historique lisible — git log --oneline se lit comme un journal de release.
Automatiser la contrainte

Ne comptez pas sur la discipline seule : un hook commit-msg (via commitlint + husky) rejette les messages non conformes avant qu'ils n'entrent dans l'historique. La convention devient alors garantie, pas espérée.

Bonnes pratiques

Le mémo collaboration
  • Taille des PR — petites & fréquentes. Une grosse PR = revue superficielle + conflits. Découper en incréments cohérents.
  • Nommage des branches — <type>/<description-courte> ou avec l'ID du ticket : feat/panier-promo, fix/PROJ-123-login-timeout. Cohérent, en minuscules, avec des tirets.
  • Rester synchronisé — rebaser régulièrement sa branche sur main pour éviter les gros conflits de fin de course.
  • Ne jamais force-push sur une branche partagée ; réserver --force-with-lease à ses propres branches.

Squash, merge commit ou rebase ?

Trois façons d'intégrer une branche, trois compromis sur l'historique :

MéthodeHistorique obtenuIdéal pour
Squash and merge1 commit propre par PR sur mainFeature branches (par défaut recommandé) : main lisible, 1 PR = 1 ligne.
Merge commit (--no-ff)Conserve tous les commits + un commit de mergeTracer précisément l'intégration ; classique en Git Flow pour les releases.
Rebase and mergeHistorique 100 % linéaire, sans commit de mergeÉquipes qui veulent une ligne droite ; suppose des commits déjà propres.

Recommandation pragmatique : squash-and-merge par défaut (un main linéaire et lisible, où chaque commit correspond à une PR), combiné à required linear history dans la protection de branche.

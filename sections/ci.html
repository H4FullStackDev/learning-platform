03 Module DevOps

Intégration Continue (CI)

Automatiser la validation à chaque commit : lint, tests, build et scan de sécurité s'exécutent tout seuls pour intégrer le code en continu, en confiance. Théorie, comparatif d'outils, et deux pipelines réels commentés.

L'idée en une phrase. L'intégration continue consiste à fusionner fréquemment le travail de chacun dans une branche partagée, en faisant valider automatiquement chaque changement par un pipeline. Objectif : détecter les régressions en minutes, pas en semaines — c'est le prolongement direct du chapitre Git.

Concepts clés

Un pipeline est l'enchaînement automatisé d'étapes déclenché par un événement (push, Pull Request, tag). Il se décompose en une hiérarchie simple qu'on retrouve, sous des noms légèrement différents, dans tous les outils :

TermeDéfinition
PipelineLe processus automatisé complet, déclenché par un événement (push, PR, tag, cron).
Stage (étape)Groupe logique de jobs, ordonné : par ex. build → test → deploy.
JobUnité de travail exécutée sur un runner, composée d'une suite de steps. Des jobs indépendants tournent en parallèle.
Step / ActionUne commande (ou une action réutilisable) au sein d'un job.
Runner / ExecutorLa machine — souvent un conteneur éphémère — qui exécute un job.
ArtifactFichier produit par un job et conservé/partagé : binaire, dist/, rapport de couverture, image.
CacheDonnées réutilisées d'une exécution à l'autre pour gagner du temps (dépendances node_modules, couches Docker…).

Anatomie d'un pipeline

Un pipeline CI typique enchaîne des stages, dont certains contiennent plusieurs jobs exécutés en parallèle :

Lint
eslint
Test
test · node 18 test · node 20
Build
build → dist/
Sécurité

Le stage « Test » illustre la parallélisation : deux jobs (Node 18 & 20) tournent simultanément.

Exemple complet — GitHub Actions

Un pipeline Node.js réaliste : lint, tests unitaires (sur deux versions de Node en parallèle), scan de sécurité, puis build avec upload d'artifact. Commenté ligne par ligne.

.github/workflows/ci.yml
name: CI                                  # Nom affiché dans l'onglet « Actions »

on:                                       # Événements qui déclenchent le pipeline
  push:
    branches: [ main ]                    # à chaque push sur main
  pull_request:                           # et à chaque PR ciblant main
    branches: [ main ]

concurrency:                              # Évite d'exécuter deux runs pour rien
  group: ci-${{ github.ref }}            # une file d'attente par branche
  cancel-in-progress: true                # annule le run précédent si un nouveau arrive

env:
  NODE_VERSION: '20'                      # version Node centralisée (DRY)

jobs:
  # ---------- 1. LINT ----------
  lint:
    runs-on: ubuntu-latest                # runner éphémère hébergé par GitHub
    steps:
      - uses: actions/checkout@v4         # récupère le code du dépôt
      - uses: actions/setup-node@v4       # installe Node...
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'                    # ...et met en cache ~/.npm automatiquement
      - run: npm ci                       # install déterministe basé sur package-lock.json
      - run: npm run lint                 # échoue le job si le lint échoue → fail fast

  # ---------- 2. TESTS (parallèle du lint) ----------
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false                    # un échec Node 18 ne coupe pas Node 20
      matrix:
        node: [ '18', '20' ]              # 2 versions = 2 jobs lancés en parallèle
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: 'npm'
      - run: npm ci
      - run: npm test -- --coverage       # tests unitaires + rapport de couverture
      - uses: actions/upload-artifact@v4  # publie la couverture comme artifact
        with:
          name: coverage-node-${{ matrix.node }}
          path: coverage/
          retention-days: 7

  # ---------- 3. SÉCURITÉ (parallèle) ----------
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm audit --audit-level=high # échoue si vulnérabilité de niveau >= high
      - name: Scan du système de fichiers (Trivy)
        uses: aquasecurity/trivy-action@0.24.0
        with:
          scan-type: fs
          severity: HIGH,CRITICAL
          exit-code: '1'                  # casse le job si une vulnérabilité est trouvée

  # ---------- 4. BUILD (attend lint + test) ----------
  build:
    needs: [ lint, test ]                 # DAG : ne démarre qu'après le succès des deux
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run build                # produit le dossier dist/
      - uses: actions/upload-artifact@v4  # artifact réutilisé par le déploiement (CD)
        with:
          name: app-dist
          path: dist/
          retention-days: 7
Le graphe de dépendances (DAG)

Sans needs, tous les jobs démarrent en parallèle. lint, test et security tournent donc en même temps ; seul build attend (needs: [lint, test]). C'est ce graphe qui rend le pipeline rapide sans sacrifier l'ordre logique.

Le même pipeline en GitLab CI

Équivalent fonctionnel en .gitlab-ci.yml — noter la config de cache et le needs: qui transforme les stages en DAG :

.gitlab-ci.yml
stages: [ lint, test, security, build ]   # ordre par défaut des étapes

variables:
  FF_USE_FASTZIP: "true"                  # zip plus rapide pour cache & artifacts

default:
  image: node:20-alpine                   # image par défaut de tous les jobs
  cache:                                   # cache partagé, invalidé si le lockfile change
    key:
      files: [ package-lock.json ]
    paths: [ .npm/ ]
  before_script:
    - npm ci --cache .npm --prefer-offline # réutilise le cache local

lint:
  stage: lint
  script:
    - npm run lint

test:
  stage: test
  parallel:                               # matrice = jobs parallèles
    matrix:
      - NODE_TAG: [ "18-alpine", "20-alpine" ]
  image: "node:$NODE_TAG"
  script:
    - npm test -- --coverage
  coverage: '/All files[^|]*\|[^|]*\s+([\d.]+)/'  # extrait le % de couverture
  artifacts:
    paths: [ coverage/ ]
    expire_in: 1 week

security:
  stage: security
  script:
    - npm audit --audit-level=high
  # Alternative « clé en main » : les templates SAST intégrés à GitLab
  # include:
  #   - template: Security/SAST.gitlab-ci.yml

build:
  stage: build
  needs: [ lint, test ]                   # DAG : démarre dès que lint + test sont verts
  script:
    - npm run build
  artifacts:
    paths: [ dist/ ]                       # artifact récupérable par le job de déploiement
    expire_in: 1 week

Cache & parallélisation : accélérer le pipeline

Deux leviers font l'essentiel de la vitesse. Le cache évite de retélécharger/recompiler ce qui n'a pas changé (dépendances, couches Docker). La parallélisation exécute simultanément les jobs qui ne dépendent pas les uns des autres.

Cache

  • Dépendances — cache: 'npm' (setup-node) ou une clé basée sur le lockfile : on ne réinstalle que si package-lock.json change.
  • Bonne clé de cache — dérivée du hash du fichier de verrouillage, pour une invalidation automatique et fiable.
  • Couches Docker — le cache de build (BuildKit / cache-from) réutilise les couches inchangées (voir le chapitre Docker).
cache explicite — GitHub Actions
# Cache manuel (quand setup-node ne suffit pas, ex. build compilé)
- uses: actions/cache@v4
  with:
    path: |
      ~/.npm
      .next/cache
    key: ${{ runner.os }}-build-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-build-

Parallélisation

En exécutant lint, test et security ensemble plutôt qu'à la suite, on passe d'un temps cumulé à un temps maximal. Sur notre exemple :

lint
2 min
test
5 min
security
3 min
build
4 min
05 min10 min

Séquentiel : 2 + 5 + 3 + 4 = 14 min  ·  Parallèle (build après test) : ≈ 9 min — soit ~35 % plus rapide, sans changer une seule ligne de test.

Bonnes pratiques

Le mémo CI
  • Fail fast — placer les vérifications les plus rapides (lint, format) en premier, pour couper immédiatement en cas d'erreur évidente.
  • Pipelines rapides (< 10 min) — au-delà, les développeurs contournent la CI. Cache + parallélisation + tests ciblés.
  • Séparer build / test / deploy — des stages distincts : on build une fois, on teste l'artifact, puis on le déploie (jamais rebuild par environnement).
  • Un artifact immuable — le même binaire/image traverse tous les environnements (dev → staging → prod).
  • Rendre la CI déterministe — npm ci (pas npm install), versions épinglées, actions taguées.
Gestion des secrets : ne jamais commiter de secret

Un token, une clé API ou un mot de passe ne doit jamais figurer dans le code ou un fichier YAML. On les stocke dans le coffre de secrets du CI (GitHub : Encrypted secrets ; GitLab : CI/CD variables masquées & protégées) et on les injecte à l'exécution :

# On référence le secret, on n'écrit jamais sa valeur
- run: ./deploy.sh
  env:
    API_TOKEN: ${{ secrets.API_TOKEN }}   # injecté et masqué dans les logs

# Encore mieux pour le cloud : OIDC, aucun secret de longue durée à stocker
permissions:
  id-token: write                         # GitHub échange un jeton court avec AWS/GCP

Complément indispensable : un scan de secrets (gitleaks, trufflehog) dans le pipeline pour rattraper une fuite accidentelle avant qu'elle n'atteigne main.

On a désormais un artifact validé et immuable en sortie de CI. Les chapitres suivants s'en emparent : Docker pour l'empaqueter, puis CD / GitOps pour le déployer automatiquement.
